# Regular MUD 상호작용 다양성 구조 감사

> 기준: `origin/main` `9b12513` (2026-09-10)
> 범위: `data/mud/regular_*.json` 28개, `js/mudSimulators.js`, `js/mudEngine.js`, 상호작용 계약·감사 스크립트
> 성격: 읽기 전용 감사. 게임 코드와 MUD JSON은 수정하지 않았다.

## 결론

사용자가 느낀 **“동그란 버튼 3회 탭의 반복”은 구조적으로 확인된다.** 다만 전달받은 분석의 분모와 원인 설명에는 정정이 필요하다.

- 전체 155개 시뮬레이터 중 102개가 JSON에 핫스팟 배열을 선언하며, **102개 전부 정확히 3개**다.
- 핫스팟 배열 102개는 모두 `drawPaleoActivity()`를 사용한다. JSON에서 반지름을 따로 지정한 곳은 0개이고, 76개는 세 좌표 배치까지 동일하다.
- 필수 시뮬레이터 112개 중 104개(92.9%)가 원형 핫스팟 계열이다. 103개(92.0%)는 완료 목표도 `3`이다. 학생의 정상 진행 경로를 설명하기에는 이 분모가 가장 유용하다.
- 데이터에는 interaction 이름이 4개 있지만 Regular 런타임 처리 방식은 사실상 2개다. `resource-allocation`과 `reflection`은 별도 동작 없이 `hotspot-discovery`와 같은 `processPaleoDiscovery()`로 연결된다.
- 기존 “반복 탭 내성” 감사가 통과한 것과 이번 문제는 모순이 아니다. 기존 감사는 **같은 단서 중복 탭으로 게이트를 우회하는가**를 검사했고, 이번 감사는 **서로 다른 단계가 같은 조작 문법을 반복하는가**를 검사한다.

따라서 해결 방향은 96개 또는 102개 장면의 일괄 재작성도, 단순한 버튼 모양 변경도 아니다. 역사적 사고 행동을 기준으로 재사용 가능한 interaction 계약을 설계하고, 서로 다른 세 단계에 먼저 적용해 수업 관찰 뒤 확대해야 한다.

## 2. 시각·입력 반복성

`drawSim()`은 `currentSimulator.hotspots`가 있으면 다른 시대별 레거시 렌더러보다 먼저 `drawPaleoActivity()`로 보낸다. 이 공통 렌더러는 다음을 고정한다.

- 미발견 채우기: 반투명 흰색
- 발견 채우기: 주황색 `#f59e0b`
- 글꼴: 굵은 11px Pretendard
- 표시 모양: `ctx.arc()` 원형
- 기본 판정 반지름: 캔버스 짧은 변의 14%
- 실제 표시 반지름: 판정 반지름의 68%

JSON 102개 중 개별 `radius`를 선언한 곳은 0개다. 세 좌표 배치는 14종뿐이며, 다음 한 배치가 76개(74.5%)에 사용된다.

```text
(0.22, 0.48) / (0.50, 0.65) / (0.78, 0.48)
```

전달 분석의 “동일 색상”은 일부 과장이다. 미발견·발견 **채우기 색**은 같지만 미발견 원의 테두리는 `scene`/`mode` 팔레트에 따라 달라질 수 있다. 그러나 모양·크기·폰트·상태 변화·대체 버튼 배열은 공통이므로 학생 체감상 동일한 조작이라는 결론은 유지된다.

## 3. 전달 분석에서 바로잡을 부분

### 3-1. “구석기 기본 sequence가 전 시대에 복제”된 것은 아니다

`processOrderedHotspot()`에 `['dry-grass', 'branches', 'stone']` fallback이 남아 있는 것은 사실이다. 그러나 Regular의 `ordered-hotspot` 60개 중 **59개가 각 단계의 sequence를 명시**한다. 유일한 미명시 사례는 구석기 IF 재시도 단계다.

전 시대에 복제된 것은 구석기 **sequence 값**이 아니라, “원형 세 곳을 정해진 순서 또는 아무 순서로 누른다”는 **조작 문법**이다.

### 3-2. 완료조건 재설계가 숫자만 바꾼 것도 아니다

기존 반복 탭 보강 작업은 여러 `text-reading`·`battle-gauge`·`culture-touch`·슬라이더 활동을 핫스팟 계약으로 전환했다. 예를 들어 `regular_bronze_age:3`은 반복 슬라이더에서 흙 경사로·통나무 굴림대·공동 노동의 고유 단서 확인으로 바뀌었다.

이 작업은 “같은 곳 연타로 통과” 문제를 해결했지만, 해결 수단을 공통 3핫스팟으로 통일하면서 **입력 안전성은 높이고 조작 다양성은 낮추는 교환**을 만들었다. 당시 목표에는 합리적이었지만 이제 별도 후속 설계가 필요하다.

### 3-3. “4분 완료 = 지루함”은 아직 가설이다

기록된 사실은 1단원 2·3차시 활동이 4분 이내에 끝났고, 학생들이 유물 활용·경쟁·타이쿤 아이디어를 제시했다는 것이다. 학생이 반복 탭 때문에 지루했다고 직접 말한 기록은 확인되지 않았다. `BACKLOG.md`도 원인을 선택지 난이도·완료 조건·읽기 속도·교실 내 정보 공유로 나눠 확인하도록 적고 있다.

따라서 상호작용 반복성이 짧은 완료 시간이나 이탈을 유발한다는 문장은 **실험 가설**로만 유지해야 한다.

### 3-4. 96개 장면 전체가 같은 오버레이를 쓴다는 표현도 현재 기준과 다르다

현재 Regular 데이터에는 108개 scene 선언과 101개 고유 scene 키가 있다. Phase 38 계획의 96은 당시 예상치였고, 완료 보고에서도 97로 정정됐다. 또한 Phase 37·38의 일부 scene은 원래 핫스팟 없는 전체 화면 게이지형이었다.

현재 확실히 같은 공통 오버레이를 쓰는 범위는 JSON 핫스팟 배열이 있는 102개 단계다.

## 4. 더 중요한 구조 문제

### 4-1. 스키마 이름과 실제 행동이 다르다

`resource-allocation`은 자원을 나누지 않고, `reflection`은 생각을 구성하거나 표현하지 않는다. 두 타입 모두 “서로 다른 원을 한 번씩 누른다”로 끝난다. interaction 이름이 교육적 의도를 표현하지만 엔진이 그 의도를 실행하지 않는 **의미적 계약 불일치**다.

### 4-2. `ordered-hotspot`의 순서가 항상 역사적으로 필요한 것은 아니다

60개 `ordered-hotspot` 중 instruction에 `차례`, `순서`, `먼저`, `마지막`, `→`처럼 순서를 명시한 단계는 5개뿐이다. 나머지에는 실제 인과·시간 순서가 있는 단계도 있지만, 독립된 자료 세 개를 “모두 확인·비교”하는 단계도 섞여 있다.

그런데 런타임은 잘못된 순서로 누르면 항상 “A보다 먼저 B를 준비해야 합니다”라고 말한다. `김홍도 풍속화 → 판소리 → 탈춤`, `팔만대장경 → 직지 → 벽란도 기록`처럼 본질적으로 독립된 자료에 임의 순서를 강제하면, 입력 규칙을 역사적 관계로 오해하게 만들 수 있다.

### 4-3. 기존 자동 감사에는 다양성 축이 없다

`scripts/_tap_resistance_rule.py`는 JSON 핫스팟, 고유 action, `uniqueActions`, 레거시 중복 거부, 최소 조작 수 중 하나가 있으면 반복 탭 위험에서 제외한다. 이는 **게이트 우회 방지 검사**로는 옳다.

하지만 다음은 검사하지 않는다.

- 연속 단계가 같은 interaction family를 반복하는가
- interaction 이름과 실제 handler가 같은 의미인가
- 순서가 없는 자료에 `ordered-hotspot`을 썼는가
- 핫스팟 수·좌표·형태가 과도하게 동일한가
- 학생이 자료를 해석하지 않고 라벨 순서만 외워 통과할 수 있는가

따라서 기존 감사의 “판단 스테이지 반복 탭 위험 0건”을 “상호작용 품질 문제 0건”으로 읽으면 안 된다.

## 5. 권고: 전면 교체 대신 3단계 수직 파일럿

새 메커닉을 시대별 장식으로 늘리는 대신 **역사적 사고 행동**에 맞춰야 한다.

| 사고 행동 | 조작 후보 | 기존 자산 재사용 | 파일럿 예시 |
|---|---|---|---|
| 공간 근거로 선택 | 지도 지점 선택 후 근거 확인 | 이미 지원하는 `hotspot-choice` | 삼국의 한강·교역로 판단 |
| 자료 분류·비교 | 카드를 두 범주에 탭하여 배치 | 미니게임 카드 UI·DOM 버튼 | 조선 신분 자료 또는 고려 문화 자료 |
| 원인과 결과 연결 | 원인 카드와 결과 카드를 짝짓기 | 기존 원인·결과 미니게임 개념 | 토지 조사→소유 변화→농민 부담 |

첫 파일럿은 다음 경계를 지킨다.

1. 기존 102개 장면을 일괄 수정하지 않는다.
2. 서로 다른 시대·사고 행동의 대표 단계 3개만 고른다.
3. 캔버스 드래그를 필수로 하지 않고, 44px 이상 DOM 버튼으로 전체 흐름을 수행할 수 있게 한다.
4. `simulator_contract.json`과 `scripts/03_validate_mud_integrity.py`·`04_validate_mud_contract.py`를 데이터보다 먼저 확장한다.
5. `scripts/05_test_simulator_runtime.js`에 정상·오입력·중복 입력·재시도 상태를 추가한다.
6. 태블릿 세로·가로 및 키보드 흐름을 검증한다.
7. 학생 3명 이상에게 기존 3핫스팟 단계와 새 단계의 이해도·완료 시간·재미·오입력을 비교한 뒤 확대 여부를 정한다.

새 타입을 한꺼번에 여러 개 만드는 대신 첫 구현에서는 기존 `hotspot-choice` 1개와 새 범용 계약 1개만 사용하는 편이 안전하다. 분류와 인과 연결을 하나의 `card-placement` 계약으로 일반화할 수 있는지는 구현 계획에서 검토한다.

## 6. 우선순위 판단

- 심각도: 진행 불가나 데이터 손상은 아니므로 P0가 아니다.
- 교육적 영향: Regular 정상 경로의 92%에 걸친 반복 문법이므로 국소 UI 문제가 아니다.
- 증거 수준: 구조 반복은 확정, 학생 지루함·학습 저하는 미검증 가설이다.
- 권고 상태: **P1 후보 / priority-review-needed**.
- 다음 문서: 사용자 승인 후 `implementation_plan_regular_interaction_diversity_pilot.md`.
