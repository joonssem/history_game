## §0 네 창 공통

### 0-1. 이번 라운드의 성격 — 넓히지 않는다

라운드 1·2에서 만든 것은 모두 운영 사이트에 나가 있지만 **학생 관찰은 아직 0회**다. 그 사이 Codex red team 감사(`docs/audits/claude_four_track_red_team_audit.md`)가, 자동 검증을 모두 통과한 결과물에서 **학생이 잘못 배울 수 있는 의미 결함**을 여럿 찾았다. 나의 연표 시대 역전, 주장 요소를 빼고 통과하는 관문, 해석 카드를 사건처럼 배열하게 한 설계, 유적 수치 오류다. 모두 2026-09-14에 고쳤다(`DECISIONS.md` D-030).

그래서 라운드 3은 **새 편·새 페어·새 게임을 만들지 않는다.** 이미 만든 것이 사실과 의미 면에서 맞는지 검증하고, 수업 관찰을 바로 할 수 있게 준비한다. 네 창 모두 "red team이 아직 보지 않은 영역"을 스스로 red team 한다고 생각하면 된다.

### 0-2. D-030 요약 — 모든 창이 알아야 할 규칙

1. **주장이 여러 요소를 말하면 요소마다 근거를 요구한다.** `requiredCategories`의 요소는 문자열(필수) 또는 배열(그중 하나 이상), 같은 범주의 서로 다른 자료가 모두 필요하면 `requiredEvidenceIds`.
2. **민감 주제 편은 `requireLimit: true`로** 자료의 한계 선택을 필수로 둔다.
3. **순서 배열에는 날짜로 순서가 확인되는 사건만** 넣는다. 연도 없는 해석은 의미 질문으로.
4. **시대 순서 판정은 기간이 겹치지 않을 때만** 한다. 유물 설명의 차시 번호는 연대순이 아니다.
5. 스크립트는 "조건이 구조적으로 성립하는가"까지만 본다. **문장의 뜻과 근거가 맞는지는 사람이 읽고 판단한다.** 이번 라운드의 핵심 작업이 바로 이것이다.

### 0-3. 사실 확인 규칙

- 수치·연도·"최대/최초" 같은 단정은 **공식 출처 원문**(국가유산포털, 국립중앙박물관, 국사편찬위원회 우리역사넷, UNESCO 등)과 대조한다. 기억이나 추측으로 확인했다고 적지 않는다.
- 원문으로 확인되면 정정하고, `sourceNote` 또는 해당 데이터의 출처 필드에 **확인 날짜와 근거 문구**를 남긴다.
- 원문으로 확인되지 않으면 오류로 단정하지 말고 **"짐작할 수 있다·단서가 된다" 범위로 표현을 낮춘다.** 그 판단도 기록한다.
- 확인한 것 / 고친 것 / 낮춘 것 / 판단을 보류한 것을 **표로** `BACKLOG.md` 말미에 남긴다. 고치지 않은 이유도 기록 대상이다.

### 0-4. 작업 환경 — 지난 라운드의 사고 두 가지

- **worktree는 이미 만들어 두었다.** 각 창은 자기 경로로 `cd`만 한다. `git worktree add`를 다시 실행하지 않는다.
- **셸 작업 위치가 다음 명령에도 그대로 남는다.** 2026-09-14 통합 중 한 명령이 main 체크아웃으로 `cd`한 뒤, 이어진 문서 추가 명령이 worktree가 아니라 main 체크아웃에 써졌다. 파일을 쓰는 명령은 **절대경로를 쓰거나 `git -C <worktree>`를 쓴다.** 커밋 직전에는 `git status --short`로 **바뀐 파일 목록이 의도와 같은지** 확인한다.
- 포트·`preview_start` 이름은 그대로다: `gate-grammar`(8801) / `artifact-site`(8802) / `activity-loop`(8803) / `inquiry-console`(8804). `.claude/launch.json`은 수정·커밋하지 않는다.
- 공용 런타임 파일을 고치면 캐시버스터를 올리고, **그 파일을 쓰는 다른 편 하나를 실제로 열어** 확인한다(라운드 2 §0-1).

### 0-5. 사용자 판단 대기 — 구현하지 않는다

아래는 사용자가 아직 결정하지 않았다. **어느 창도 구현하지 않는다.** 설계상 문제를 발견하면 보고만 한다.

- 설계 문서 4건: `mud_perspective_task_design.md`, `implementation_plan_inquiry_progressive_disclosure.md`, `story_mud_relationship.md`, `implementation_plan_map_evidence_canvas_role.md` 옵션 B
- 조작대의 map-evidence 캔버스 옵션 A 승인 여부(이미 배포됨)
- 근거 인벤토리 기본 펼침 여부
- `claude-deep-prehistoric` 브랜치의 미반영 7커밋

## §1 관문 설계실 — `feat/mud-gate-grammar` · `.worktrees/claude-gate-grammar`

### 1-1. 파일럿 4편 의미 검토표 (주 작업)

고려 문화·신석기·삼국·근대 개항 4편의 **16개 관문 전부**를 사람 눈으로 읽고 표를 만든다. `docs/audits/inquiry_pilot_semantic_review.md`.

관문마다 적을 것:

| 편·관문 | 문법 | 정답이 말하는 요소 | 그 요소를 받치는 자료·근거 | 빠진 요소 | 조치 |
|---|---|---|---|---|---|

- `commit-revise`: 정답 선택지 문장의 **모든 요소**를 `requiredEvidenceIds` 자료가 받치는가. **알려진 공백**: 근대 1관문 정답 "개항의 계기가 되었지만 … 불평등 조항"에서 **"개항의 계기"를 받치는 자료가 없다**(필수 자료 두 장이 모두 불평등 조항). 이것부터 처리한다.
- `sequence`: 카드가 모두 **날짜로 순서가 확인되는 사건**인가(D-030 3). 의미 질문의 정답이 카드에서 실제로 도출되는가.
- `map-evidence`: 장소·근거·한계 세 정답이 서로 같은 이야기를 하는가. `labels`가 그 편에 맞는가.
- `claim-evidence`: 주장 8개의 요소별 근거 요구는 2026-09-14에 넣었다. **요구가 주장 문장보다 과하거나 모자라지 않은지** 다시 읽는다.
- 오답 선택지·오답 피드백이 **정답을 노출하지 않으면서** 왜 부족한지 말하는가.

데이터로 고칠 수 있는 것은 고치고, 구조 변경이 필요한 것은 보고한다. 역사 서술을 새로 지어내지 않는다. 고칠 때는 §0-3 사실 확인 규칙을 따른다.

### 1-2. 수업 관찰 체크리스트

Codex의 첫 인계(`claude_code_interaction_diversity_handoff_20260910.md` §6 P0)가 요구했는데 **아직 아무도 만들지 않았다.** `docs/plans/classroom_observation_inquiry_pilot.md`에 작성한다.

- 대상: 파일럿 4편, 학생 3명 이상. 아이패드 가로 1180×820과 휴대폰 390×844.
- 공통 지표: 편당 완료 시간(목표 7~12분), 무작위 클릭·전수 대입 행동, 두 자료를 연결해 **말로** 설명하는지, 오답 뒤 스스로 수정하는지, 교사 개입 횟수, 조작이 막힌 지점.
- 편별 관찰 포인트: 근대 개항 편에서 한쪽 극단을 고르는 학생이 있는지, 삼국 편에서 세 나라 근거를 다 모으는 데 막히는지, 마지막 관문에서 앞 관문 근거를 기억하는지(인벤토리를 여는지) 등.
- 교사가 한 장으로 들고 쓸 수 있는 **기록 양식**을 포함한다.
- `EXPERIMENTS.md`에 새 실험 항목을 **관찰 → 가설 → 실험 → 결과 → 다음 결정** 형식으로 추가한다. 결과 칸은 비워 둔다.

### 1-3. 하지 않는 것

새 편 전환, `perspective` 구현, `js/` 수정.

## §2 대조실 — `feat/artifact-site-comparison` · `.worktrees/claude-artifact-site`

### 2-1. 기존 9개 페어 사실 검증 (주 작업)

Codex는 **신규 유적 페어 2개만** 감사했고, 거기서 암사동 집터 수 오류(100여 개 → 실제 20여 기)가 나왔다. 나머지 9개는 같은 수준의 검증을 받은 적이 없다.

- 9개 페어의 `traits`, `claim` 빈칸 정답, `scholarPerspective`, `evidenceCards`에서 **수치·연도·단정 표현**을 모두 뽑아 공식 출처와 대조한다(§0-3).
- 특히 볼 것: 제작 연대(`cmp_science_1`은 현존 실물이 세종 당시 원본이 아니라고 이미 적어 둠 — 같은 종류의 문제가 다른 페어에도 있는지), "학자들은 ~라고 봐"라는 학계 관점 문장이 **실제로 합의된 해석인지 아니면 한 가지 설명을 단정한 것인지**, 초등 5학년에게 맞지 않는 서술.
- 결과 표: 페어 · 문장 · 출처 대조 결과(일치/오류/확인 불가) · 조치(정정/완화/유지) · 근거 URL과 확인 날짜.

### 2-2. 유적 출처 필드 공백 정리

red team 감사가 지적했다. 출처 정책(`docs/plans/artifact_site_source_policy.md`)은 `site.checkedAt`·`site.hasPhoto`를 요구하지만, 유적을 비교 대상 자체로 쓴 두 페어(`kind: "site"`)는 날짜를 문장 속에만 두었다.

- 정책 문서에 `kind: "site"` 대상의 확인 날짜·사진 유무 **저장 위치**를 정한다.
- 두 유적 페어 데이터에 반영한다. **렌더링에 영향이 없어야 한다** — `js/`는 고치지 않는다.
- 가능하면 `scripts/01_validate_game_data.py`가 그 필드를 검사하게 한다.

### 2-3. 하지 않는 것

신규 페어, 다시 보기 구현, 실물 사진 추가, `js/` 수정.

## §3 연결 공방 — `feat/extended-activity-loop` · `.worktrees/claude-activity-loop`

### 3-1. 나의 연표 수정 인수 검토

기획 세션이 red team RT-01을 고치면서 **이 창 소유 파일 `js/miniGames.js`의 나의 연표 판정을 바꿨다.** 유물 설명의 차시 번호 대신 `era`별 기간(`getArtifactTimelineRange`)으로 정렬하고, 기간이 겹치지 않는 유물끼리만 순서를 판정한다(`isChronologicallyValidOrder`). 소유자로서 검토한다.

- 기간표가 합리적인가. 너무 넓어서 **당연히 물어야 할 순서를 놓치는** 쌍, 너무 좁아서 **틀린 순서를 강요하는** 쌍이 있는가. 36개 유물 전체의 쌍을 뽑아 확인한다.
- **`data/artifacts.json`의 `era` 라벨 자체가 틀린 유물**을 찾는다. 예: `art_12` 판옥선·천자총통(임진왜란, 1592)이 `조선 후기`로 되어 있다. 이 파일은 **읽기만** 한다(소유 밖) — 찾은 것은 표로 보고한다.
- 판정 코드를 고친다면 캐시버스터를 올린다.

### 3-2. 원인과 결과·기본 연표 사실·의미 검증 (주 작업)

red team이 **아직 보지 않은 영역**이다. `data/causeEffectChains.json` 4세트와 `data/timeline.json` 2세트.

- 사건 카드가 모두 **날짜로 확인되는 사건**인가, 해석이 사건처럼 끼어 있지 않은가(RT-05 계열).
- `hint`의 인과 서술이 사실과 맞는가. "A 때문에 B가 일어났다"가 **실제로 합의된 인과**인가, 한 가지 설명을 단정한 것인가.
- 특히 라운드 1에서 새로 만든 **1·2단원 세트**(고려·조선)를 공식 출처와 대조한다(§0-3).
- 결과 표를 `BACKLOG.md`에, 정정·완화는 데이터에 반영한다.

### 3-3. 하지 않는 것

새 미니게임, 스토리 관계 정의안 구현, `data/artifacts.json` 수정.

### 4-2. D-030 판정 회귀 테스트

`scripts/05_test_simulator_runtime.js`에 2026-09-14 추가된 판정 규칙의 단위 테스트를 넣는다.
