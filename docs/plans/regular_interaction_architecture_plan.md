# Regular MUD 상호작용 전체 구조 계획

## 상태

- 작업: `TASK-20260910-05`
- 상태: `proposed / pilot-evidence-required`
- 범위: 개인형 Regular MUD의 상호작용·완료 판정·피드백·확장 순서
- 비범위: Deep-dive, 정적·실시간 협동 MUD, 배포 인프라, 개인정보 처리
- 전제: [`implementation_plan_regular_interaction_diversity_pilot.md`](./implementation_plan_regular_interaction_diversity_pilot.md)의 고려 문화 파일럿을 먼저 구현·검증한다.

이 문서는 장기 방향을 설명하지만 아직 `ARCHITECTURE.md`, `ROADMAP.md`, `DECISIONS.md`에 채택된 결정은 아니다. 파일럿 결과와 사용자 승인을 거쳐 필요한 항목만 승격한다.

## 1. 목표 구조

현재는 Canvas에서 발생한 클릭과 완료 카운터가 가깝게 결합되어 있다. 목표 구조는 **표현, 의미 행동, 판정, 진행**을 분리한다.

```text
MUD stage JSON
├─ scene                 시대·장소의 시각 맥락
├─ interaction           학생이 수행할 의미 행동
├─ completion            완료로 인정할 학습 상태
└─ feedback              오개념·수정·성취 피드백
        ↓
Scene Renderer           배경·지도·유물 표현
        ↓ itemId
Interaction Adapter      탭·버튼·키보드를 의미 행동으로 정규화
        ↓ semantic action
Task Evaluator           관계·순서·근거 충분도 판정
        ↓ incomplete / revise / complete
MudEngine                선택지 해제·단계 이동·보상
```

Canvas 좌표는 입력 방법일 뿐 정답이 아니다. 완료 여부는 evaluator가 만든 의미 상태만 결정한다.

## 2. 모듈별 책임

| 계층 | 목표 책임 | 핵심 원칙 |
|---|---|---|
| `MudEngine` | MUD·스테이지 생명주기, 진행 게이트, 보상 | 역사적 정답 규칙을 넣지 않음 |
| `MudSimulators` | Canvas 장면과 hit test | 클릭 성공을 완료로 간주하지 않음 |
| `MudInquiry` | DOM 상호작용, task adapter, evaluator registry | task별 계약을 작게 유지 |
| MUD JSON | 문구, 카드, 관계, 허용 답, 오개념 피드백 | 실행 코드·HTML 금지 |
| 계약·검증기 | 지원 값, 참조 무결성, 완료 가능성 검사 | 런타임과 같은 어휘 사용 |
| 감사 스크립트 | 반복 조작, 인지 행동 분포, 위험 신호 보고 | 콘텐츠를 자동 수정하지 않음 |

기존 `mudSimulators.js`의 대형 분기를 한 번에 재작성하지 않는다. 새 inquiry 활동만 별도 모듈에 추가하고, 레거시는 실제 마이그레이션되는 단계부터 경계를 정리한다.

## 3. 상태 모델

상태는 생명주기에 따라 세 층으로 분리한다.

| 상태 | 생명주기 | 예시 | 저장 |
|---|---|---|---|
| 입력 상태 | 현재 상호작용 | 선택 카드, 카드 순서, 현재 배치 | 메모리 |
| MUD 실행 상태 | 한 MUD를 여는 동안 | 획득 근거, 최초 판단, 수정 여부, 힌트 사용 | 메모리 |
| 사용자 지속 상태 | 여러 방문 | 유물·배지·완료 상태 | 기존 localStorage만 유지 |

`attempts`, `misconceptionFlags`, `hintsUsed`는 개인정보가 아니더라도 파일럿 동안 장기 저장하지 않는다. 실제 수업에서 필요성이 확인되기 전에는 서버 전송이나 학생별 분석을 추가하지 않는다.

## 4. 표준 interaction 체계

### 4-1. 유지할 레거시 입력

| interaction | 유지 조건 | 향후 처리 |
|---|---|---|
| `hotspot-discovery` | 실제 관찰·탐색이 목표이고 발견 뒤 별도 판단이 필요 없는 경우 | 정보 열람으로 명확히 표시하거나 inquiry의 관찰 단계에 연결 |
| `ordered-hotspot` | 제작 절차·시간·인과 순서가 역사적으로 의미 있는 경우 | sequence 근거 필드와 감사 규칙 추가 |
| `hotspot-choice` | 장소 선택 자체가 결정이고 각 지점이 다른 결과로 이어지는 경우 | 좌표와 같은 DOM 대체 입력 유지 |
| `gauge` | 반복 행동의 양이 학습 맥락을 실제로 표현하는 경우 | 단순 탭 채우기는 점진적으로 축소 |

### 4-2. 새 표준 추론 계약

`inquiry-task` 하나를 두고 task adapter를 제한된 목록으로 운영한다.

| task.type | 인지 행동 | 대표 UI |
|---|---|---|
| `commit-revise` | 가설 설정·수정 | 첫 판단, 근거 공개, 최종 판단 |
| `sequence` | 절차·시간·인과 배열 | 순서 카드 |
| `classify` | 공통점·차이점·범주화 | 카드와 2~3개 영역 |
| `map-evidence` | 공간 자료와 해석 연결 | 지도 지점 + 근거 목록 |
| `claim-evidence` | 주장·근거·한계 구성 | 논증 보드 |
| `tradeoff` | 제한 자원과 결과 비교 | 토큰 배분·결과 저울 |

새 task는 아래 세 조건을 모두 만족할 때만 추가한다.

1. 기존 task의 데이터 조합으로 표현할 수 없다.
2. 최소 두 개 이상의 MUD에서 재사용할 구체적 후보가 있다.
3. 정답·복수 정답·피드백·접근성 입력을 검증 가능한 JSON 계약으로 설명할 수 있다.

`resource-allocation`과 `reflection`은 현재 실제 행동과 이름이 일치하지 않는다. 전수 변경하지 않고 해당 단계가 마이그레이션될 때 `tradeoff` 또는 적절한 task로 옮기며, 남은 레거시는 감사 보고서에서 별도로 추적한다.

## 5. 완료 판정 계약

완료 전략은 두 가지로 명시한다.

```text
counter          기존 호환: 진행량 + 최소 행동 수
validated-state  신규 기본: task evaluator가 타당한 상태라고 판정
```

`validated-state` evaluator의 공통 반환값은 다음과 같다.

```jsonc
{
  "status": "incomplete | revise | complete",
  "feedbackKey": "misconception_or_success_id",
  "earnedEvidence": ["evidence-id"],
  "quality": "observer | connector | historian"
}
```

- `incomplete`: 필요한 행동이 덜 끝남
- `revise`: 제출했지만 관계나 근거가 부족함. 진행은 유지하되 완료하지 않음
- `complete`: 기본 학습 기준 충족
- `quality`: 순위 점수가 아니라 같은 활동 안의 사고 깊이 피드백

기본 보상은 `complete`에서 동일하게 지급한다. `historian` 등급은 추가 문구나 선택형 심화 해금에만 사용하고 필수 진도를 막지 않는다.

## 6. 콘텐츠 작성 계약

각 시뮬레이터 단계는 다음 질문에 답할 수 있어야 한다.

| 필드 | 작성 질문 |
|---|---|
| `learningAction` | 학생이 관찰·분류·비교·추론·논증 중 무엇을 하는가? |
| `prompt` | 무엇을 판단해야 하는가? |
| `evidence` | 어떤 자료가 판단을 뒷받침하는가? |
| `misconceptions` | 사실 오류가 아니라 어떤 과잉 일반화·혼동이 예상되는가? |
| `successRule` | 무엇을 하면 이해했다고 볼 수 있는가? |
| `feedback` | 왜 부족한지 비교 가능한 단서를 주는가? |
| `accessibilityLabel` | 그림 없이도 대상을 식별할 수 있는가? |

오답·함정은 다음 범주만 사용한다.

- 관련은 있지만 현재 주장을 직접 뒷받침하지 않는 자료
- 한 사례를 전체 시대로 확대하는 과잉 일반화
- 원인과 결과 또는 제작과 보관을 혼동한 설명
- 시기·관점·자료 범위를 잘못 연결한 설명

사실이 아닌 가짜 유물, 우스꽝스러운 선택지, 화면 구석의 작은 표식은 난이도로 사용하지 않는다.

## 7. 한 MUD 안의 난이도 곡선

전역 시대순 난이도는 두지 않는다. 학생이 차시를 비선형으로 선택할 수 있기 때문이다. 대신 각 MUD 안에서 다음 네 역할을 구성한다.

| 위치 | 권장 역할 | 예시 task |
|---:|---|---|
| 1 | 관찰하고 가설 세우기 | discovery 또는 `commit-revise` |
| 2 | 정리하고 관계 만들기 | `sequence`, `classify` |
| 3 | 맥락·인과·공간 추론 | `map-evidence`, `tradeoff` |
| 4 | 앞의 근거로 종합하기 | `claim-evidence` |

모든 MUD가 정확히 네 단계일 필요는 없다. 3단계라면 `관찰 → 관계 → 종합`, 5단계 이상이면 중간에 비교·관점 task를 추가한다.

## 8. 전체 마이그레이션 순서

### Phase 0 — 기준선 감사: 완료

- 상호작용 분포, 3핫스팟 반복, 좌표 중복, 순서 없는 sequence와 런타임 alias를 기록했다.
- 감사 결과는 구현 우선순위를 위한 기준선이며 자동 변환 지시가 아니다.

### Phase 1 — 고려 문화 수직 파일럿

- 대상: `regular_goryeo_culture` 한 편
- 산출: `inquiry-task` 계약, 네 task, 접근성 UI, 자동·브라우저 테스트
- 게이트: 기술 검증 + 학생 최소 3명 수업 관찰

### Phase 2 — 전체 28종 인지 행동 매핑

코드를 바꾸기 전에 각 필수 단계를 다음 중 하나로 분류한다.

```text
유지 가능한 관찰
실제 순서
분류·비교
공간·인과 추론
주장·근거 종합
실제 trade-off
학습 목적 불명확 — 콘텐츠 재기획 필요
```

산출물은 MUD별 `현재 행동 / 목표 행동 / 유지·변환 이유 / 민감성 / 예상 비용` 표다. 시대별로 새 조작을 배정하지 않고 학습 행동이 같은 단계는 같은 task를 재사용한다.

### Phase 3 — 대표 유형 묶음

파일럿에서 살아남은 계약만 사용해 서로 다른 학습 유형의 MUD 4~6편을 고른다.

- 제작·기술: 실제 절차 순서
- 정치·제도: 원인·결과 또는 trade-off
- 생활·문화: 분류·비교
- 전쟁·영토: 지도 근거·공간 판단
- 사회 변화: 관점·주장·근거

민감한 전쟁 피해·식민 지배 소재는 게임화 표현을 별도 검토하고 초기 대표 묶음에서 제외한다.

### Phase 4 — 소규모 배치 확장

- 한 번에 4~6개 MUD만 변환한다.
- 같은 파일을 두 에이전트가 수정하지 않도록 역할·worktree를 분리한다.
- 각 묶음은 `계획 → 콘텐츠 검토 → 구현 → 자동 회귀 → 브라우저 → 수업 또는 교사 플레이`를 독립적으로 통과한다.
- 실패한 task는 다음 묶음으로 확산하지 않는다.

### Phase 5 — 재플레이와 유물 연결

핵심 판정이 안정된 뒤에만 다음을 검토한다.

- 다른 관점·자료 조합의 선택형 재플레이
- 해금 유물을 정답 도구가 아닌 추가 질문·자료 열람 도구로 사용
- 앞선 MUD 근거를 후속 탐구에서 다시 쓰는 연결
- 공개 경쟁이 아닌 개인 탐구 숙련도 표현

## 9. 우선순위 결정 기준

각 MUD의 변환 우선순위는 다음 가중치로 검토하되 자동 점수만으로 확정하지 않는다.

| 기준 | 높은 우선순위 신호 |
|---|---|
| 반복 위험 | 네 단계가 모두 3핫스팟·동일 좌표·target 3 |
| 학습 손실 | feedback을 읽지 않아도 선택지 정답을 쉽게 알 수 있음 |
| 재사용 가치 | 새 task를 다른 MUD에도 적용할 수 있음 |
| 콘텐츠 안전성 | 비민감 주제이고 정답 관계를 출처로 확인하기 쉬움 |
| 수업 시점 | 가까운 차시에 실제 수업 검증이 가능함 |
| 구현 위험 | 전용 Canvas·레거시 상태 의존이 적음 |

## 10. 품질 게이트

### MUD 단위

- 필수 단계 중 최소 한 단계는 `validated-state`로 역사적 관계를 판정한다.
- 같은 interaction/task가 세 단계 이상 연속되면 교육적 이유를 데이터 또는 계획에 적는다.
- 마지막 단계는 가능하면 앞서 수집한 근거를 한 번 이상 재사용한다.
- `ordered`는 순서의 역사적 이유를 설명할 수 있어야 한다.
- Canvas 없이도 필수 활동을 완료할 수 있다.

### 저장소 단위

- 기존 무결성·계약·소스·런타임 검증을 모두 유지한다.
- 신규 감사는 interaction 이름뿐 아니라 실제 task와 완료 전략을 집계한다.
- `interaction` 이름과 실제 런타임 handler가 다른 alias를 새로 만들지 않는다.
- 레거시 변환률을 목표로 삼지 않는다. 학습 목적에 맞는 기존 활동은 유지한다.

### 수업 단위

- 완료 시간만 보지 않고 근거 사용, 수정, 힌트, 교사 개입을 함께 관찰한다.
- 학생 피드백은 즉시 요구사항으로 승격하지 않고 `EXPERIMENTS.md`에 가설과 결과로 남긴다.
- 속도가 빠르다는 이유만으로 문장량이나 클릭 수를 늘리지 않는다.

## 11. 역할 분담

| 역할 | 담당 |
|---|---|
| 기획·점검 | MUD별 learningAction, 계약, 우선순위, 수용 기준 승인 |
| content agent | 카드·오개념·피드백의 역사적 정확성과 5학년 문장 검토 |
| implementation agent | 엔진·UI·JSON·검증기 구현 |
| audit agent | 전수 집계와 회귀 신호 등록. 직접 수정하지 않음 |
| integration agent | 브랜치 확인, 병합, 전체 회귀, 배포 확인 |

파일럿 구현에서는 `mudEngine.js`, `mudInquiry.js`, `mudSimulators.js`의 소유자를 한 명으로 둔다. 콘텐츠 검토자는 같은 파일을 동시에 수정하지 않고 문서 또는 리뷰로 전달한다.

## 12. 채택 전 결정할 항목

파일럿 뒤 다음 세 가지를 사용자와 확정한다.

1. `inquiry-task`가 실제로 범용 계약으로 충분한가, 아니면 task를 줄여야 하는가.
2. `관찰자·연결자·역사가`를 화면에 계속 사용할지, 수업 언어에 맞게 바꿀지.
3. 기존 미구현 `argument-builder` 계획을 이 구조로 흡수하고 해당 문서를 archive/superseded 처리할지.

확정되면 `DECISIONS.md`에 “좌표·행동 수가 아니라 의미 상태로 완료를 판정한다”는 장기 원칙을 기록하고, `ARCHITECTURE.md`와 `ROADMAP.md`에는 실제 채택된 모듈·확장 순서만 반영한다.
