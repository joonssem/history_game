- 조선 후기 시나리오는 고려 초기 활동에서 검증된 공통 엔진을 재사용하는 두 번째 실제 활동이자 10월 28일 공개수업 후보다.

## 2. 목표와 완료 정의

### 제품 목표

교사 한 명이 세션을 열고, 학생 4명이 서로 다른 고려 건국기 관점을 받아 말로 공유한 뒤, 서로 다른 두 역할의 근거를 사용해 “새 고려가 사람들을 묶기 위해 먼저 할 일”을 공동으로 설명하게 한다.

### 학습 목표

학생은 다음을 설명할 수 있어야 한다.

1. 고려의 건국과 후삼국 통일 과정에는 여러 집단의 선택과 이동이 관련되어 있었다.
2. 새 왕조가 안정되려면 지방 세력 포용, 항복 세력 대우, 이주민 수용, 백성의 부담 완화 같은 정책이 필요했다.
3. 한 역할의 자료만으로 전체 상황을 단정할 수 없으며 다른 관점의 근거가 필요하다.

### 첫 활동 완료 조건

- 교사 1명과 학생 4~8명이 실제 기기에서 세션 생성부터 종료까지 진행한다.
- 각 학생은 자기 역할의 고유 자료를 한 번 이상 말로 설명한다.
- 공동 답안은 서로 다른 역할 출처의 근거를 2개 이상 포함한다.
- 공동 답안에는 `이 자료만으로 알 수 없는 점`이 하나 포함된다.
- 같은 revision을 모둠 전원이 확인하기 전에는 완료되지 않는다.
- 새로고침·짧은 네트워크 단절 뒤 역할과 진행 상태가 복구된다.
- 세션 종료 뒤 수업 상태와 토큰이 정리된다.
- 학생 이름·학번·계정·개인 자유서술을 서버에 저장하지 않는다.

## 3. 활동 범위

### 기본 4인 역할

| 역할 | 고유 관점 | 학생이 가져와야 할 근거의 방향 |
|---|---|---|
| 신라 사신 | 항복 뒤에도 사람과 지역이 안전하게 받아들여질지 걱정한다. | 항복 세력을 함부로 대하지 않고 포용한 사례 |
| 지방 호족의 전령 | 지역 세력과 새 왕조의 관계를 살핀다. | 혼인·성씨 수여·직책 등 지방 세력 포용 방식과 한계 |
| 발해 유민 | 삶의 터전을 잃고 고려에 들어온 사람의 입장을 전한다. | 발해 유민과 대광현 일행을 받아들인 사례 |
| 마을 사람 | 전쟁과 수취가 생활에 미치는 영향을 말한다. | 백성의 부담을 줄이고 민생을 안정시키려 한 정책 |

역할명·문장·근거 범위는 Claude가 출처 검토표와 함께 확정한다. 특정 집단을 하나의 생각으로 일반화하거나 왕 한 사람의 선의만으로 통합이 완성된 것처럼 쓰지 않는다.

### 3인·5인 변형

- 3인: 한 학생에게 두 역할을 겸임시키지 않는다. 제외된 관점은 짧은 공통 자료로 제공한다.
- 5인: 다섯째 학생은 단순 서기가 아니라 북방 정세·기록 검토처럼 고유 근거와 판단권이 있는 역할을 맡는다.
- 모든 편성에서 각 학생은 `자료 확인 → 최초 판단 → 말하기 → 공동 초안 확인`을 수행한다.

### 핵심 질문

> 새 고려가 서로 다른 사람들을 한 나라로 묶기 위해 가장 먼저 해야 할 일은 무엇일까?

공동 답안의 구조는 자유 작문 대신 제한된 조합과 짧은 설명을 사용한다.

1. 우선할 정책 2개 선택
2. 서로 다른 역할의 근거 2개 선택
3. `왜 함께 필요한가`를 정해진 문장 틀로 완성
4. `이 자료만으로 알 수 없는 점` 1개 선택
5. 모둠 전원 확인

개인 최초 판단과 이유는 기기 안에만 보존하고, 서버에는 완료 여부와 시각만 둔다.

## 4. 수업 흐름

목표 시간은 첫 리허설 기준 8~10분이다.

| 단계 | 학생 활동 | 시스템 게이트 | 목표 시간 |
|---|---|---|---:|
| 입장 | QR 또는 수업 코드로 입장 | 세션·정원·토큰 검증 | 1분 |
| 역할 자료 | 자기 역할 카드와 근거 확인 | 다른 역할의 비공개 본문은 보이지 않음 | 1분 30초 |
| 최초 판단 | 정책 하나와 짧은 이유 선택 | 제출 전 다음 단계 잠금 | 1분 |
| 말하기 | 각자 자료를 모둠에 설명 | 전원 `설명했어요` 확인 | 2분 |
| 공동 해석 | 정책 2개·근거 2개·한계 1개 조합 | 서로 다른 역할 근거 강제 | 2분 30초 |
| 전원 확인 | 같은 공동 초안을 검토 | 초안 변경 시 기존 확인 무효 | 1분 |
| 인계 | 발표용 문자열 또는 교사 화면 표시 | 완료 모둠만 열림 | 1분 |

`sticky-wall` 연계는 첫 실제 활동의 필수 조건이 아니다. 먼저 온라인 협동 게이트를 검증하고, 외부 서비스 없는 교사 화면·화이트보드 인계를 기본으로 둔다. 공개수업 전 별도 리허설에서만 sticky-wall 연계를 추가 검증한다.

## 5. 구현 범위

### P0 — 첫 실제 활동에 반드시 필요한 것

- 서버가 검증하는 다중 시나리오 레지스트리와 `scenarioId`·`scenarioVersion`

- 개인 최초 판단 완료 상태
- 모둠 공동 초안과 revision
- 서로 다른 역할 근거 2개 이상 검증
- 자료 한계 선택
- 전원 동일 revision 확인
- 교사 단계 진행, pause/resume, 모둠별 도움 요청
- 새로고침·재접속 복구

- sticky-wall 직접 인계
- 교사 대시보드의 더 자세한 병목 통계
- 학생 자유 문장 입력
- 애니메이션·게임성 확장

P1은 첫 활동 결과 없이 구현하지 않는다.

## 6. 시나리오 계약 원칙

Claude는 기존 고조선 상수와 화면 문장을 공통 엔진에서 분리한다. 구체적인 파일명은 현행 구조 확인 후 정하되 계약에는 최소 다음 개념이 있어야 한다.

```ts
type CooperativeScenario = {
  id: string;
  version: number;
  publicMeta: {
    title: string;
    lesson: string;
    recommendedMinutes: number;
  };
  roles: RoleDefinition[];
  groupSizes: Record<3 | 4 | 5, GroupLayout>;
  sharedPrompt: SharedPrompt;
  teacherStages: TeacherStage[];
};
```

- 전체 역할 본문과 정답 검증 정보는 서버 전용으로 둔다.
- 클라이언트는 자기 역할과 현재 단계에 필요한 DTO만 받는다.
- 활성 세션은 생성 당시 version을 유지한다. 배포 중 최신 정의로 몰래 바꾸지 않는다.
- 잘못된 ID·알 수 없는 version·권한 밖 역할 조회는 서버에서 거부한다.
- 고조선 현행 흐름은 호환 fixture로 남아 생성·입장·편성·종료 회귀가 계속 통과해야 한다.

### 안전한 작업 절차

1. 현재 main의 계획 문서 변경을 먼저 하나의 커밋으로 고정한다.
2. Claude는 그 커밋을 기준으로 `feat/cooperative-live-early-goryeo` 같은 전용 브랜치와 별도 worktree를 만든다.
3. 공유 중인 `C:\chatGPT_test\history_game` 폴더에서 브랜치를 바꾸지 않는다.
4. Claude는 시작 전에 `TASK-번호 | apps/cooperative-live 및 고려 활동 | implementation/content agent | 상태: DOING`을 claim한다.
5. Claude 작업 중 Codex는 해당 worktree와 소유 파일을 쓰지 않는다.
6. Claude가 구현·테스트·walkthrough를 같은 브랜치에 커밋하고 `READY_FOR_AUDIT` SHA를 전달한다.
7. Codex는 그 SHA를 읽기 전용으로 감사한다. 수정 요청은 감사 문서 또는 메시지로만 전달한다.
8. 수정 라운드가 끝난 뒤 integration 역할이 전체 회귀와 Go/No-go를 수행하고 main에 병합한다.

이미 Claude가 별도 브랜치에서 작업 중이라면 새 브랜치를 만들지 않는다. 현재 브랜치·worktree·기준 SHA·미커밋 파일을 먼저 확인하고, 해당 경로의 소유권을 Claude에게 유지한 채 이 계획만 인계한다. 같은 공유 폴더에서 작업 중이라면 어느 한쪽이 브랜치를 전환하지 말고 Claude 작업을 별도 worktree로 옮긴 뒤 계속한다.

## 8. Claude 구현 작업 묶음

### T0 — 소유권 고정과 베이스라인

- 전용 branch/worktree와 기준 SHA를 기록한다.
- 현행 고조선 시나리오, 교사 세션, 학생 입장, 3~24명 편성, 복구, 종료 삭제의 현재 테스트를 확인한다.
- 고려 활동에 필요한 P0와 기존 구현의 차이를 체크리스트로 만든다.

완료 기준: 수정 경로가 이 계획의 Claude 소유 범위에만 있고, 다른 세션의 미커밋 변경이나 DOING claim과 겹치지 않는다.

### T1 — 콘텐츠 패킷과 계약 fixture

- 러프 스케치의 4+1 역할 카드, 최초 판단, 공통 질문, 정책 옵션, 근거 라벨, 자료 한계, 교사 힌트를 작성한다.
- 각 학생 문장에 대응하는 출처 URL·열람일·주장 범위를 기록한다.
- 3·4·5인 배치에서 역할 고유성과 공통 자료 보충 규칙을 fixture로 고정한다.

완료 기준: 모든 역할에 고유 근거·판단·말하기 의무가 있고, 과잉 일반화·현대 가치의 단순 투사·정답 유도 표현이 없다.

### T2 — 다중 시나리오와 고려 역할 수직 관통

- 고조선 하드코딩을 시나리오 계약 뒤로 옮기고 고려 초기 시나리오를 등록한다.
- 교사 생성 화면에서 시나리오를 선택하고 서버가 ID·version을 검증한다.
- 4개 독립 학생 세션에서 각자 자기 역할 자료만 받도록 한다.
- 최초 판단은 로컬 보존, 서버에는 완료 상태만 저장한다.

완료 기준: 고조선 회귀가 유지되고, 고려 활동에서 다른 학생 역할 본문이나 비공개 정답 정보를 조회할 수 없다.

### T3 — 공동 초안과 전원 확인

- 모둠별 공동 초안과 단조 증가 revision을 구현한다.
- 서로 다른 역할 근거 2개, 정책 2개, 한계 1개를 서버에서 검증한다.
- 초안이 바뀌면 이전 revision의 전원 확인을 무효화한다.
- 다수결·편집자 단독 저장·오래된 revision 확인으로 완료되지 않게 한다.

완료 기준: 모둠 전원이 같은 최종 revision을 확인해야 인계가 열린다.

### T4 — 교사 제어·복구·종료

- pause/resume 동안 학생 mutation을 서버에서 차단한다.
- 도움 요청과 교사 해제, 단계별 모둠 진행 n/N을 구현한다.
- 새로고침·탭 복귀·Wi-Fi 재접속 후 세션·역할·초안·확인 상태를 복구한다.
- 종료·TTL 정리에서 신규 테이블과 필드를 포함해 세션 데이터를 삭제한다.

완료 기준: 오래된 화면·중복 탭·종료된 토큰이 상태를 바꾸거나 다시 입장하지 못한다.

### T5 — 자동 검증과 기기 리허설 준비

- 저장소에 실제로 정의된 lint·typecheck·test·build 명령을 실행한다.
- 3·4·5인 역할 배치와 4·8·21명 세션을 자동 검증한다.
- 교사 1 + 학생 4 브라우저 수동 절차와 실패 시 정적 대체 절차를 앱 README에 기록한다.
- 첫 실제 활동용 교사 1장 운영 체크리스트를 준비한다.

완료 기준: 자동 검증 결과와 미실행 항목이 결과 문서에 구분되어 있고, 실제 기기 시험을 재현할 수 있다.

## 9. 검증 계획

### 자동 검증

Claude는 구현 시 `apps/cooperative-live/package.json`에 실제 존재하는 명령을 기준으로 실행한다. 계획 단계에서 명령 이름을 새로 가정하지 않는다.

필수 검증 범위:

- 시나리오 ID·version·참조 무결성
- 3·4·5인 역할 배치와 고유 근거
- 다른 교사 세션·다른 모둠·다른 역할 접근 거부
- 공동 초안 revision 경쟁과 전원 확인 무효화
- pause/resume과 오래된 제출 차단
- 새로고침·재접속·중복 탭
- 종료·TTL 삭제와 기존 토큰 거부
- 4명, 8명, 21명 편성·진행·종료
- production client bundle의 비공개 역할 본문·정답 정보 노출 여부
- 수업 코드·토큰·역할·개인 응답의 console/log 비노출
- 기존 고조선 생성·입장·편성·진행·종료 회귀

### 1차 리허설 — 성인 또는 교사 4~8명

- 목표: 기능 고장과 진행 안내의 모호함을 먼저 찾는다.
- 기록: 입장 시간, 각 단계 시간, 도움 요청, 재접속, 발화 누락, 공동 답안 완성 여부.
- 통과: 치명적 오류 없이 8~10분 안에 완료하고 전원이 자기 근거를 말한다.

### 2차 시험 — 실제 학생 소규모

`EXP-009` 형식으로 다음만 관찰한다.

- 역할 자료가 실제 발화를 만드는가?
- 다른 학생의 자료를 듣지 않고 완료하려는 행동이 있는가?
- 최초 판단과 공동 답안 사이에 근거를 든 수정이 생기는가?
- 교사 개입 없이 이해하기 어려운 문장이나 단계는 무엇인가?
- 8~10분 수업 시간 안에 마치는가?

학생 반응은 즉시 기능 요구사항으로 승격하지 않는다. `관찰 → 가설 → 작은 수정 실험 → 결과 → 다음 결정`로 기록한다.

## 10. 조선 후기 공개수업으로 넘기는 조건

고려 초기 활동이 다음 조건을 통과한 뒤에만 같은 엔진에 조선 후기 콘텐츠를 추가한다.

1. 4~8명 실제 기기 리허설 완료
2. 실제 학생 소규모 시험에서 진행 불가 오류 없음
3. 전원 역할 발화와 서로 다른 역할 근거 2개 사용 확인
4. 공동 초안 revision·전원 확인이 교사 개입 없이 이해됨
5. 재접속·pause/resume·종료 삭제 정상
6. 개인정보 운영 체크리스트와 실제 배포 환경 일치 확인

실패 항목이 콘텐츠 문제면 고려 문안만 Claude가 보정한다. 공통 엔진 문제면 Claude가 최소 범위로 수정하고 고조선·고려 회귀를 함께 돌린다. 조선 후기 고유 기능을 고려 시험에 미리 끼워 넣지 않는다.

## 11. 승인 요청 범위

이 계획 승인으로 허용되는 것은 Claude가 T0~T5를 구현하고 Codex가 그 결과를 읽기 전용으로 감사하는 것까지다. 실제 학생 접속은 개인정보 환경 일치 확인과 4~8명 리허설 통과 뒤 별도 Go 판정으로 연다. 조선 후기 콘텐츠 구현은 고려 첫 활동 결과를 확인한 뒤 후속 계획에 따라 시작한다.
