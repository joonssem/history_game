## D-019 — 실시간 협동 MUD의 백엔드는 Convex로 하고 별도 앱으로 분리한다

- 상태: **폐기 (2026-10-15, [D-038](../../../DECISIONS.md#d-038--convex-실시간-협동-활동을-취소하고-교사-모둠-편성-정적-협동으로-돌아간다))**. 이하 원래 기록은 보존한다. 채택 방향 (2026-09-06, 프로젝트·코드 미구현)
- 근거: 2026-09-04 실제 수업(`EXPERIMENTS.md` `EXP-006`)에서 교사가 꼽은 최대 제약이 "모둠 진행 상황을 볼 수 없음"이었다. 교사 대시보드와 실시간 개입은 기기별 정적 구조로는 만들 수 없다. 기존 `js/mudEngine.js`는 전역 객체·고정 DOM·Canvas 기반 개인 플레이 엔진이라 네트워크 상태 저장소로 교체하기 어렵다.
- 규칙: 실시간 협동 MUD는 기존 GitHub Pages 앱을 개조하지 않고 별도 Next.js 앱으로 만든다. 공동 상태의 기준은 Convex이며, 화면 컴포넌트에 별도의 게임 상태 머신이나 WebSocket 서버를 만들지 않는다. 배포는 Vercel이며 기존 Pages 운영을 대체하지 않는다.
- 권한: 클라이언트가 보낸 `teacherId`·`playerId`·`roleId`를 신뢰하지 않고, 모든 공개 함수에서 인증 → 세션 소유·참가 → 모둠 → 허용 단계 순으로 검증한다. Convex에는 Supabase RLS에 해당하는 선언적 정책이 없으므로 권한 규칙을 직접 구현한다.
- 개인정보: 이름·학번·이메일·음성·화면 녹화·기기 고유 ID·위치를 수집하지 않는다. 수업 한정 가명 코드만 사용하고 보관 기간과 삭제 경로를 구현 전에 확정한다.
- 미검증: Convex Auth는 beta이고 Next.js 서버 인증 지원은 실험 단계다. 요금·무료 한도 안에서 수업 사용량을 감당하는지, 학교 Wi-Fi에서 21대 동시 접속이 되는지는 확인하지 않았다. 첫 수직 슬라이스에서 인증·복구를 먼저 검증하고, 실패하면 인증 계층만 재선정한다.
- 설계 문서: [`COLLABORATIVE_MUD_PLAN.md`](../cooperative-live/COLLABORATIVE_MUD_PLAN.md), [`COLLABORATIVE_MUD_ARCHITECTURE.md`](../cooperative-live/COLLABORATIVE_MUD_ARCHITECTURE.md), [`COLLABORATIVE_MUD_MVP.md`](../cooperative-live/COLLABORATIVE_MUD_MVP.md)

## D-020 — 백엔드는 하나만 운영하고 Supabase 계획은 D-019 결정에 따라 보류한다

- 상태: 보류 결정 (2026-09-06)
- 근거: `D-017`은 기존 정적 앱의 익명 플레이 로그용으로 Supabase를 후보로 두었고, `D-019`는 신규 실시간 앱에 Convex를 채택했다. 두 계획을 모두 유지하면 1인 유지보수자가 BaaS 두 개를 동시에 운영하게 된다. 어느 쪽도 아직 구현되지 않아 지금이 정리 시점이다.
- 규칙: `D-017`의 Supabase `play_events`는 `보류`로 두고 새로 착수하지 않는다. 최소 플레이 진단 로그가 다시 필요해지면 Supabase 프로젝트를 새로 만들지 말고 Convex 위에서 재설계할지 먼저 검토한다. `TECH_STACK.md`·`ARCHITECTURE.md`·`ROADMAP.md`·`PRD.md`의 Supabase 서술은 "보류된 후보"로 읽는다.
- 예외: 이 결정은 백엔드 서비스 선택에만 적용된다. `D-017`의 개인정보 원칙(이름·학번·계정·기기 ID·위치 미수집, 클라이언트에 secret 키 미포함)은 백엔드와 무관하게 계속 유효하다.
- 재검토 조건: Convex의 요금·학교 네트워크·인증 검증이 실패해 백엔드를 바꿔야 할 때 이 결정을 다시 연다.

## D-021 — 학생의 판단 내용은 서버에 저장하지 않는다

- 상태: 채택 방향 (2026-09-06, 실시간 앱 미구현)
- 근거: 앱은 이름을 수집하지 않지만 교사가 `모둠·번호 = 실제 학생` 대응표를 갖고 있어, 서버의 개인 응답과 결합하면 특정 학생의 판단이 식별된다. Convex Cloud는 미국 동부·아일랜드 리전만 제공하므로 어느 쪽도 국내 보관이 아니다. 정적 버전에는 없던 위험이다. 한편 2026-09-04 수업([`EXP-006`](../../../EXPERIMENTS.md))에서 교사가 꼽은 제약은 "모둠 진행 상황을 볼 수 없음"이었지 "학생이 무엇을 골랐는지 볼 수 없음"이 아니었다. 대시보드에 필요한 것은 답이 아니라 진행 상태다.
- 규칙 1 — **개인 응답 비저장**: 최초·수정 판단의 선택지와 이유, 역사 비교 응답은 학생 기기의 세션 한정 메모리나 `sessionStorage`에만 둔다. 서버에는 제출 여부와 시각만 저장한다. 모둠 법 초안·확정과 법 확인 응답(`agree`/`discuss`)은 공동 산출물이므로 서버에 둔다. 기기의 개인 응답도 활동 종료 시 지우고 다음 협동 MUD로 넘기지 않는다.
- 규칙 2 — **보관 0일**: `수업 종료`가 곧 삭제다. 세션 하위 rooms/players/actions/events와 입장·복구 자격을 함께 지운다. 교사가 남기고 싶은 관찰은 앱 밖에 옮겨 적는다.
- 규칙 3 — **대응표를 앱에 넣지 않는다**: 학생 명단 업로드 기능을 만들지 않는다. 편의를 이유로 추가하면 규칙 1·2가 무의미해진다.
- 포기하는 것과 대체: 교사가 화면에서 개인 선택을 열어 볼 수 없다 → 그 자리로 가서 학생 화면을 본다. 판단 변경을 서버에서 집계할 수 없다 → 학생 기기 요약 화면과 모둠 대표 발표로 대체한다(2026-09-04 수업의 실제 운영 방식).
- 남는 조건: 제출 여부와 모둠 산출물은 수업 중 잠시 외부 서버에 존재한다. **개인정보 처리 근거와 Convex·Vercel 처리위탁·국외 처리 조건을 착수 전에 확인한다**(`BACKLOG.md` P1-COLLAB-PRIVACY). 국외 처리가 불가하면 [D-019](../../../DECISIONS.md#d-019--실시간-협동-mud의-백엔드는-convex로-하고-별도-앱으로-분리한다)를 다시 연다. 이 결정의 설계는 백엔드와 무관하게 유효하다.
- 적용 문서: [`COLLABORATIVE_MUD_ARCHITECTURE.md`](../cooperative-live/COLLABORATIVE_MUD_ARCHITECTURE.md) §2-3·§3 스키마·§8, [`COLLABORATIVE_MUD_MVP.md`](../cooperative-live/COLLABORATIVE_MUD_MVP.md) §5·§6·§7·§11

## D-023 — 실시간 협동 MUD의 학생 식별은 활동마다 새로 만들고 종료 시 끊는다

- 상태: 채택 방향 (2026-09-07, 구현 전)
- 활동 시작: 학생은 협동 MUD마다 무작위로 제시된 공용 목록에서 새로운 호를 고른다. 시작 시점까지 고르지 않은 학생에게는 서버가 호를 무작위 배정한다. 대기 중인 학생은 서버가 해당 활동의 모둠과 역할에 무작위로 배치하며, 이전 활동의 호·참여 ID·모둠 정보를 재사용하지 않는다.
- 활동 중: 교사 대시보드는 실제 이름이나 개인 답 대신 호·모둠 구성·현재 단계·제출 인원·경과·도움 요청을 보여 준다. 교사는 진행 속도와 구성에 따라 미리 정한 힌트 또는 심화 상황을 모둠 단위로 보낸다.
- 활동 종료: 세션, 참여 ID, 호, 모둠·역할 배치, 진행 상태, 제출 상태·시각, 힌트·심화 이력, 입장·복구 자격을 삭제한다. 기기에 남은 세션 한정 응답도 지우며 다음 협동 MUD로 기록을 넘기지 않는다.
- 실패 대응: 자동 삭제 실패를 교사에게 알리고 수동 강제삭제를 제공한다. 공급자 로그·백업의 잔존기간은 [P1-COLLAB-PRIVACY](../../../BACKLOG.md)에서 별도 확인한다.

## D-035 — 조선 후기 협동 활동은 실제 앱 계약에 맞춘다; 앱 코드는 Codex, 콘텐츠는 Claude

- 상태: 채택 (2026-09-17, 사용자 결정)
- 배경:
  - Codex 감사(`docs/audits/joseon_late_packet_red_team_audit.md`)가 T1 등록을 NO-GO로 판정했다.
  - 이유: 계획서 모델(대상–주장–근거–한계)로 만든 패킷이 실제 앱(`apps/cooperative-live/convex/scenarios.ts`) 계약과 다르다. 앱 계약은 정책 2개 + 역할 근거 2개 + 연결 + 한계이고, 역할마다 `firstChoices`·`evidence[]`를 가지며, `sources`가 필수다.
- 규칙:
  1. 기준 계약은 **실제 앱의 `CooperativeScenario`**(고려 초기 `early-goryeo-unity`와 같은 모양)다. 계획서 §4 타입은 폐기한다.
  2. "누구에게" 대상 선택은 앱 필드로 추가하지 않는다. `connections` 문구와 `interventions.deepen`에 녹인다.
  3. 역할별 `sharePrompt`는 앱에 필드가 없으므로 교사 자료로 옮긴다. `commonPrompt`는 `sharedPrompt.question`이 된다.
  4. 역할마다 앱 화면에 보이는 근거는 `evidence[0]` 하나다. 역할당 대표 근거 하나를 고른다.
  5. `target_landlord`처럼 대응하는 역할 근거가 없는 선택지는 두지 않는다.
  6. **앱 코드(`apps/cooperative-live/**`) 등록·서버·테스트는 Codex가 한다.** Claude는 앱 계약 모양의 콘텐츠 JSON과 출처, 검증 스크립트까지만 만든다.
- 감사 수용·기록(red team 정책):
  - 수용: C1-01(계약 불일치), C1-03(대상·공통 근거 미연결), C1-04(추론 문장을 사실처럼 씀), C1-05(`scripts/15` 문장 분리·메모 제거 오탐, 런타임 계약 미검사).
  - **부분 수용·기록만**: C1-02(Pages 공개). 예측 가능한 URL의 초안 JSON은 정리한다. 그러나 고조선 정적 협동(`cooperative-mud/gojoseon-law/scenario.js`)과 고려 초기 앱(`convex/scenarios.ts`)도 역할 비공개 본문을 공개 저장소에 두고 있다. 공개 저장소에서 "서버 전용"은 **학생 화면에 보내지 않는다**는 뜻이지 비밀 보장이 아니다. 위협 모델은 "학생이 수업 중 다른 역할 자료를 쉽게 보지 못함"으로 둔다. 조선 후기에만 다른 기준을 적용하지 않는다.
