# 구현 계획 — 역할 기반 협동 역사 MUD 파일럿

상태: `draft` / 사용자 승인 대기

## 1. 목적

텍스트 MUD의 핵심 구조인 공간감·역할 정체성·불완전한 정보·공동 의사결정을 초등 역사 수업에서 검증한다. 최초 목표는 실시간 멀티플레이 구현이 아니라 다음 학습 행동의 발생 여부를 확인하는 것이다.

```text
정보 읽기 → 친구에게 설명하기 → 근거로 토의하기 → 모둠 결정 → 결과 성찰
```

대상 시나리오는 임진왜란 한산도 작전이며, 기존 Regular MUD와 유물 비교 활동을 대체하지 않는 별도 수업형 Deep-dive 후보로 취급한다.

## 2. 범위

### 포함

- Room 3개: 수군 본진, 정찰·정보 공간, 전투 해역
- 역할 4개: 정찰관, 지형·항해관, 무기·보급관, 기록·지휘 보좌관
- 공통 상황 카드 1개와 역할별 핵심 단서 각 1~2개
- 모둠 공유판에 단서를 올리는 행동
- 역사적 딜레마 1개와 선택지 3개
- 근거 카드 선택
- 모둠 결정 및 결과 텍스트 변화
- 실제 역사와 자신의 선택을 비교하는 성찰 단계
- 실패 후 안전한 재도전
- 역할별 단서 확인·공유·투표·완료 여부를 확인할 수 있는 최소 진단

### 제외

- Firebase, WebSocket, Socket.io, React, Next.js 도입
- 다중 기기 접속과 실시간 계정·세션 관리
- 자유 채팅과 대화 원문 저장
- 교사 실시간 관제 대시보드
- 음성 인식
- 점수 순위표·개인 경쟁·공개 랭킹
- 영구 사망·유물 소실
- 시나리오 전체 역사 분기와 다중 엔딩 대량 생성

## 3. 학습 목표와 수용 기준

학생은 활동 후 다음을 할 수 있어야 한다.

1. 역할별 단서와 공통 상황을 구분해 말할 수 있다.
2. 모둠원이 발견한 정보를 듣고 자신의 판단을 수정하거나 보완할 수 있다.
3. 작전 선택에 사용한 역사적 근거를 하나 이상 선택할 수 있다.
4. 자신의 모둠 선택과 실제 역사적 전개를 비교할 수 있다.

파일럿은 다음 조건을 모두 확인할 때 다음 단계로 승격한다.

- 대부분의 모둠에서 역할별 단서 공유가 발생한다.
- 특정 역할 또는 한 학생만 결정을 독점하지 않는다.
- 투표 전에 근거 카드나 역할 단서를 다시 확인한다.
- 학생이 결과보다 선택 이유를 설명한다.
- 교사가 1회 수업에서 안내·진행·정리를 감당할 수 있다.

## 4. 권장 사용자 흐름

```text
시나리오 시작
→ 역할 카드 배정
→ Room/상황 확인
→ 개인 단서 확인
→ 모둠 공유판 등록
→ 작전 선택 토의
→ 근거 선택
→ 모둠 투표·결정
→ 세계 반응 텍스트
→ 실제 역사 비교
→ 성찰 질문
```

한 기기에서 역할 카드를 탭으로 전환하는 방식을 기본으로 한다. 한 학생이 모든 카드를 연속으로 읽어버리지 않도록 교사는 역할 카드를 인쇄물로 배정하거나, 화면에서 역할별 확인 순서를 운영한다. 정보 공유는 공유 버튼을 눌러 공통 보드에 공개하는 방식으로 단순화한다.

## 5. 콘텐츠 설계 기준

### 역할 단서

- 각 역할 단서는 결정에 실제로 사용되어야 한다.
- 역할별 단서는 서로 중복되지 않되, 하나만으로 정답을 확정할 수 없어야 한다.
- 역할마다 “다른 친구에게 설명할 문장”을 제공한다.
- 물리적으로 한 장소에 함께 있었던 것처럼 단정하지 않고, 서로 다른 Room의 정보망으로 표현한다.

### 딜레마

- 선택지마다 이익·위험·시간 비용을 둔다.
- 정답 공략 하나로 고정하지 않는다.
- 실제 역사적 전개는 별도 카드로 제시한다.
- 학생 선택이 역사를 바꿨다고 단정하지 않고, 당시 조건에서 가능한 판단을 비교한다.

### 텍스트와 실패

- 한 화면의 기본 상황은 짧게 유지하고 세부 자료는 선택적으로 연다.
- 강제 타자기 효과를 사용하지 않는다.
- 실패는 새로운 단서와 재도전으로 이어지며 유물과 전체 진행을 삭제하지 않는다.

## 6. 현재 코드와의 통합 방향

1차 구현 승인 후에도 기존 `js/mudEngine.js`, `js/mudSimulators.js`, Deep-dive JSON을 동시에 수정하지 않는다. 파일 소유권과 구현 위치를 먼저 확정한다.

권장되는 최초 구현 형태는 기존 앱의 독립적인 파일럿 화면 또는 정적 JSON 데이터 기반의 별도 활동이다. 기존 Regular MUD 완료 상태·유물 도감·공용 엔진과 직접 결합하지 않고, 실험 결과가 확인된 뒤 연결한다.

가능한 최소 데이터 구조는 다음과 같다.

```json
{
  "id": "pilot_hansando_team",
  "rooms": [],
  "roles": [],
  "sharedClues": [],
  "decision": {},
  "reflection": {}
}
```

이는 확정 스키마가 아니라 콘텐츠 검증용 초안이다. 서버 도입 시에도 클라이언트가 임의로 세계 상태를 확정하지 않도록 권한·동시성·재접속 정책을 별도로 설계한다.

## 7. 실험 운영안

- 대상: 4인 모둠 중심의 소규모 수업
- 운영: 안내·역할 배정 5분, 탐색·공유 10분, 토의·결정 10분, 결과·성찰 10분 내외
- 수집: 교사 체크리스트와 최소 이벤트만 사용
- 기록 금지: 학생 이름, 학번, 자유 대화 원문, 기기 식별자, 공개 순위

교사 체크리스트:

- [ ] 네 역할의 단서가 모두 확인되었는가?
- [ ] 학생들이 자신의 단서를 서로 설명했는가?
- [ ] 투표 전에 근거를 다시 확인했는가?
- [ ] 역할별 참여가 균형적이었는가?
- [ ] 결과보다 선택 이유를 말했는가?

## 8. 단계별 구현 순서

1. 교과서·공식 자료와 한산도 콘텐츠 정합성 검토
2. 역할별 단서·공통 상황·선택지·근거 카드 작성
3. 종이 역할 카드 또는 클릭형 목업으로 수업 리허설
4. 정적 웹앱 파일럿 구현
5. 키보드·태블릿·모바일 회귀 확인
6. 최소 진단과 교사 체크리스트로 실제 수업 관찰
7. 결과에 따라 비동기 공유판, 다중 기기 동기화, 교사 화면 중 하나만 다음 단계로 선택

## 10. 승인 전 확인 사항

- 이 파일럿을 현재 P1인 유물 비교 활동 이후의 P2 실험으로 유지할 것인가?
- 한산도 시나리오를 일반 차시 활동이 아닌 수업형 Deep-dive로 분류할 것인가?
- 첫 수업은 4인 모둠이 역할을 하나씩 맡는 협동 실험으로 운영할 것인가? 한 기기 조작 순서와 무관하게 역할 카드는 인쇄물 또는 역할별 화면 순서로 물리적으로 분리하고, 1인이 네 역할을 모두 읽는 방식은 이 파일럿의 협동 검증으로 인정하지 않는다.
- 종이 역할 카드 또는 클릭형 목업 리허설에서 안내·기기 전달·질문 응대를 포함한 실제 시간을 측정하고, 40분 수업 안에서 충분한 전환·예비 시간을 남기도록 단계·시간 예산을 조정할 것인가?
- `deep_joseon` 4번 스테이지와 한산도·이순신·학익진 소재를 의도적으로 재사용해 개인/협동 학습 구조를 비교할 것인가? 아니라면 §8-1 콘텐츠 정합성 검토에서 다른 시나리오 후보로 교체할 것인가?
- 콘텐츠 검토 후 정적 웹앱 구현을 승인할 것인가?

## 11. Claude 검토 (2026-09-02)

이 문서의 원 작성자(기획·점검 에이전트)와 별개로, Track B 작업을 진행한 Claude 세션이 사용자 요청으로 검토했다. 아래는 승인 전 반영을 제안하는 내용이며, 원문(§1~10)은 고치지 않았다.

### 11-1. 잘된 점

- **§2 제외 목록이 정확하다**: Firebase·실시간·교사 대시보드·랭킹·영구사망을 전부 명시적으로 뺐다. INBOX.md에 먼저 나왔던 Firebase+React 실시간 버전보다 위험도가 훨씬 낮은 재설계다.
- **§4 한 기기 역할카드 탭 전환**: 실시간 서버 없이 "역할별 비대칭 정보"를 구현하는 실용적인 해법이다 — 동시성·재접속 문제 자체를 회피한다.
- **§3 승격 기준이 관찰 가능하다**: "결정 독점 없음", "투표 전 근거 재확인" 등 실제로 체크리스트화할 수 있는 조건이다.
- **§6 파일 소유권을 미리 명시**: `mudEngine.js`·`mudSimulators.js`·Deep-dive JSON을 동시에 수정하지 않는다고 먼저 못박아 뒀다 — 진행 중인 Deep-dive 게이팅 작업(`deep_prehistoric`/`deep_joseon`/`deep_modern`/`deep_three_kingdoms`)과 충돌하지 않는다.

### 11-2. 승인 전 확인이 필요한 문제 3가지

**(1) "협동"의 실제 운영 방식이 §4만으로는 불명확하다.**
"한 기기에서 역할 카드를 탭으로 전환한다"는 서술이 (a) 학생 4명이 태블릿 1대를 돌려쓰는 것인지, (b) 학생 1명이 혼자 4개 역할을 순서대로 읽는 것인지 구분되지 않는다. (b)라면 "협동 검증"이 아니라 "정보를 4조각으로 나눈 1인 플레이"가 되어 §1의 목적(공동 의사결정 검증)과 어긋난다. §4에 "역할 카드를 인쇄물로 배정"하는 대안이 잠깐 언급되지만 주 설계로 확정되어 있지 않다.
→ **제안**: §10 승인 전 확인 사항에 "한 기기를 여러 학생이 순서대로 조작하는지, 인쇄 카드로 역할을 물리적으로 분리하는지"를 명시적 항목으로 추가한다.

**(2) §7 시간 예산이 빠듯하다.**
안내 5 + 탐색 10 + 토의 10 + 성찰 10 = 35분. 초등 한 차시(40분) 대비 여유가 5분뿐이다. 같은 세션이 작성한 [`docs/audits/deep_dive_playtime_estimate.md`](../audits/deep_dive_playtime_estimate.md)에서 "구조적 추정은 실제보다 항상 짧게 나온다"(재시도·기기 전달·질문 응대 미반영)는 걸 확인했는데, 같은 위험이 이 파일럿에도 그대로 적용된다.
→ **제안**: 1차 리허설(§8-3, 종이 카드/클릭형 목업)에서 실제 소요 시간을 재고, 35분 예산에 여유를 더 두거나 단계를 줄인다.

**(3) 대상 시나리오가 기존 콘텐츠와 겹친다.**
`data/mud/deep_joseon.json`의 스테이지 4가 이미 정확히 같은 전투(한산도 대첩·이순신·판옥선·학익진·천자총통)를 다룬다 — 최근 hotspot 단서 인용까지 다듬어 둔 상태다. 의도적 재사용(같은 소재를 1인용/협동용 두 구조로 만들어 학습 효과를 비교)이라면 타당한 설계이지만, 이 문서에는 그 의도가 적혀 있지 않아 우연한 중복인지 구분되지 않는다.
→ **제안**: §1 목적에 "`deep_joseon` 4번 스테이지와 같은 소재를 다른 학습 구조로 재사용해 비교한다"처럼 의도를 명시하거나, 의도적이지 않다면 콘텐츠 정합성 검토(§8-1) 단계에서 다른 시나리오로 교체를 검토한다.

### 11-3. 결론

구조 자체는 승인해도 안전한 수준이다. §10 승인 전 확인 사항에 위 3개 항목(협동 운영 방식 확정 / 시간 여유 재검토 / 한산도 중복 의도 명시)을 추가하고 답을 받은 뒤 승인할 것을 제안한다.
