# 설계안 — `map-evidence` Canvas 역할 정리

작성: Claude (조작대, 2026-09-11) — **설계서만. 코드 변경 없음.**
상태: **제안 — 사용자 확인 대기.** 원 지시서(`claude_track1b_inquiry_console_instruction.md`) §5 절차와 라운드 2 지시서 §4-2에 따라, 이 문서로 사용자 확인을 받은 뒤에만 구현한다.

## 1. 문제

`map-evidence` 문법은 "발견 위치 자체가 근거"라는 공간 추론을 의도한다(`claude_track1a_gate_grammar_instruction.md` §3). 그런데 실제 데이터를 보면 공간이 실질적인 판정 요소가 아니다.

`regular_goryeo_culture.json`의 3관문을 예로 들면:

```jsonc
"hotspots": [
  { "id": "byeokrando-port", "label": "벽란도", "x": 0.22, "y": 0.52, ... },
  { "id": "heungdeoksa", "label": "흥덕사", "x": 0.5, "y": 0.68, ... },
  { "id": "haeinsa", "label": "해인사", "x": 0.78, "y": 0.52, ... }
],
"task": {
  "locations": [
    { "id": "byeokrando-port", "label": "벽란도", "detail": "고려 수도 개경 인근 예성강 하구에 있던 무역항", "correct": true, ... },
    ...
  ]
}
```

- 캔버스의 x/y 좌표는 **화면에 흩뿌린 위치일 뿐 판정에 쓰이지 않는다.** 세 지점을 서로 바꿔 배치해도 게임 동작은 동일하다.
- DOM 버튼(`renderChoiceGroup`)이 이미 `location.label`(장소 이름)과 `detail`(지명 설명)을 텍스트로 전부 보여 준다. 학생은 지도를 한 번도 보지 않고 이름만 읽고 골라도 100% 정답에 도달한다.
- 즉 "공간 추론"이라 부르지만 실제로는 **이름표 3개짜리 객관식**이다. `regular_neolithic`·`regular_three_kingdoms`도 같은 구조를 그대로 재사용한다(현재 `map-evidence`를 쓰는 편 3개 전부).

## 2. 접근성 제약 — 왜 "캔버스를 강제"할 수 없는가

`js/mudSimulators.js`의 캔버스는 `role="img"`이고, `mn-hotspot-actions`의 DOM 버튼이 **동등한 대체 조작**이다(`docs/handoff/claude_track1b_inquiry_console_instruction.md` §4의 "모바일 대체 조작은 접근성상 반드시 필요" 원칙, WCAG 비텍스트 콘텐츠 대체 요건). 스크린리더·저시력·모터 장애 학생은 캔버스를 볼 수도, 좌표를 정확히 클릭할 수도 없다.

그런데 "동등한 대체"의 정의상, DOM 버튼이 캔버스가 주는 정보와 **같은 정보**를 텍스트로 제공해야 한다. 캔버스만 아는 정보(좌표, 색, 아이콘)가 있고 DOM 버튼에 없다면 그건 접근성 결함이다. 반대로 DOM 버튼에 있는 정보를 캔버스가 몰라도 상관없다.

**결론:** DOM 버튼에 있는 정보로 이미 정답을 알 수 있는 한, 캔버스를 "봐야만" 풀리게 만들 방법은 없다 — 만들면 그 순간 DOM 경로가 캔버스보다 정보가 부족해져 접근성이 깨진다. 두 경로는 항상 **같은 조작 난이도**를 가져야 한다. 따라서 목표를 "캔버스를 안 보면 못 푼다"가 아니라 **"캔버스가 장식이 아니라 실제로 같은 정보를 공간으로도 전달한다"**로 재정의한다.

## 3. 옵션

### 옵션 A — 런타임만 변경 (권장, 1차)

데이터 스키마를 바꾸지 않는다. `js/mudSimulators.js`/`js/mudInquiry.js`만 고친다.

- 캔버스 클릭과 DOM 버튼 클릭이 **정확히 같은 시각 결과**를 내도록 되먹임을 강화한다. 지금은 `selectMapLocation`이 상태만 바꾸고 `drawSim()`을 다시 부르는데, 캔버스 쪽에 "선택됨" 표시(예: 클릭한 핀 강조 링)가 있는지 확인하고 없으면 추가한다. DOM 버튼에서 골라도 캔버스가 즉시 그 지점을 강조해, **두 경로가 하나의 조작을 반영하는 하나의 화면**이라는 인상을 준다(지금은 DOM만 봐도 되니 둘이 분리된 느낌).
- 오답을 골랐을 때 캔버스에 **틀린 지점과 정답 지점의 관계**를 시각으로 보여준다(예: 오답 지점은 흐리게, "여기 말고 이 지역을 보세요"처럼 화살표나 범위 표시). 텍스트 피드백(`location.feedback`)은 이미 있으므로, 캔버스는 그 텍스트가 가리키는 곳을 **같이 가리키는 보조 채널**이 된다 — 정보량은 같지만 공간 감각이 있는 학생에게 추가 단서가 된다.
- 지도 배경 자체를 장식(단색 배경 위 텍스트)에서 **실제 지형 스케치**(해안선·강·산)로 바꾸고, 핀을 그 지형 위에 배치한다. 위치가 완전히 임의가 아니라 "예성강 하구"라면 실제로 해안 쪽에, "산속 절"이라면 산 쪽에 놓아 **그림이 지명 설명과 어긋나지 않게** 한다. 지금처럼 좌표가 무의미하지 않고, 최소한 "이 그림이 이 설명과 모순되지 않는다"는 최소 기준은 채운다.
- 이 옵션은 **판정 로직을 바꾸지 않는다.** DOM 버튼만으로도 여전히 완전히 풀 수 있다(접근성 유지). 다만 캔버스가 그 풀이를 시각으로 뒷받침하는 "장식"에서 "보조 설명"으로 격상된다. 냉정히 말하면 §1의 핵심 문제("공간이 선택 사항")를 완전히 해소하지는 못한다 — 대신 위험 없이 지금 바로 할 수 있는 개선이다.

### 옵션 B — 데이터 스키마 확장 (더 근본적, 관문 설계실 조율 필요)

지도가 실제로 판별에 필요한 정보를 나르게 하려면, **DOM 버튼의 정답 단서와 지도의 정답 단서가 같은 것**이어야 한다. 예를 들어 지금처럼 "벽란도"라는 이름으로 즉시 정답이 드러나는 대신:

```jsonc
"locations": [
  { "id": "byeokrando-port", "label": "강 하구에 자리한 무역항", "detail": "..." },
  { "id": "heungdeoksa", "label": "내륙 산기슭의 절", "detail": "..." },
  { "id": "haeinsa", "label": "산속 깊은 곳의 사찰", "detail": "..." }
]
```

과 함께 캔버스도 그 지형적 특징(강 하구/산기슭 아이콘)을 그린다면, 텍스트만 읽어도(접근성 유지) "지형 특징 → 정답"을 추론해야 하고, 캔버스는 **같은 추론을 그림으로도** 할 수 있게 돕는 진짜 보조 경로가 된다. 지명을 직접 말하지 않으므로 단순 암기 매칭이 아니라 "이 자료가 묘사하는 곳이 지도의 어디인가"를 실제로 따져야 한다.

이건 `task.locations[].label`을 지명에서 특징 서술로 바꾸는 **콘텐츠 변경**이라 `data/mud/regular_*.json` 소유권(관문 설계실)을 건드린다. 3편(고려·신석기·삼국) 모두 같은 방식으로 다시 써야 하고, 새 필드(`hotspot.terrain` 또는 유사)가 필요할 수 있어 `simulator_contract.json`·`scripts/04_validate_mud_contract.py`도 손봐야 한다. **이번 라운드 범위 밖이며, 관문 설계실과 별도로 합의해야 한다.**

## 4. 권장안

1차로 **옵션 A**만 이번 트랙(조작대) 단독으로 진행한다. 판정 로직·데이터 스키마를 건드리지 않고 3편 모두에 동일하게 적용 가능하며, 관문 설계실의 승인이나 작업 없이 착수할 수 있다.

옵션 B는 "지도가 실제로 필수 정보를 나른다"는 원래 목표를 완전히 채우지만, 콘텐츠 재작성과 스키마 확장이 필요하므로 **별도 라운드에서 관문 설계실과 함께 사용자 확인을 받은 뒤** 진행할 안건으로 남긴다.

## 5. 검증 계획 (승인 시)

- `regular_goryeo_culture`·`regular_neolithic`·`regular_three_kingdoms`의 `map-evidence` 관문에서 DOM 버튼만으로도 여전히 완전히 통과 가능한지(접근성 회귀 없음) 확인한다.
- 캔버스 클릭 → DOM 상태 반영, DOM 클릭 → 캔버스 강조 반영이 양방향으로 즉시 동기화되는지 확인한다.
- 1180×820, 820×1180에서 캔버스가 잘리거나 핀이 겹치지 않는지 확인한다.
- 콘솔 error/warning 0건.
