## 1. 문제와 목표

실제 학생 21명 중 2명이 활동 화면에 들어가지 못했지만 서버에는 21명이 남았고, 이전 입장에서는 22명으로 표시되기도 했다. 복구할 수 없는 참가자 행이 전원 관문의 분모에 포함되면서 `전체 다음 단계`가 작동하지 않았다. 같은 수업에서 교사 개입 이력, `설명했어요` 오류 복구, 모둠별 진행 제어, QR 가독성 문제도 확인됐다.

이번 계획의 목표는 다음 네 가지다.

1. 기기를 잃거나 탭을 닫은 학생을 **같은 역할·모둠·진도 자리**에 안전하게 재연결한다.
2. 복구할 수 없는 참가자는 교사가 제외해 해당 모둠의 관문 분모를 다시 계산한다.
3. 정상 모둠은 다른 모둠의 장애와 관계없이 다음 단계로 진행한다.
4. 교사가 개입 전송 결과와 차단 사유를 즉시 이해하고, 학생은 실패한 행동을 안전하게 재시도한다.

학생 이름·학번·계정·개인 판단 내용은 새로 저장하지 않는다. 모든 추가 상태는 세션 종료 시 기존 데이터와 함께 삭제한다.

## 3. 핵심 설계 결정

### 3-1. 참가자는 즉시 삭제하지 않고 상태로 관리한다

`players`에 세션 한정 상태를 추가한다.

- `participationStatus`: `active | removed` — 기존 행은 마이그레이션 없이 `undefined`를 `active`로 해석한다.
- `lastSeenAt`: 학생 화면의 최근 heartbeat 시각.
- `removedAt`, `removedBy`: 교사가 제외한 경우의 세션 한정 감사 흔적.
- `recoveryTokenHash`, `recoveryTokenExpiresAt`: 특정 자리를 다시 연결하는 일회용 자격. 원문은 저장하지 않는다.

관문·완료 수·확인 분모는 `active` 참가자만 사용한다. `removed` 행은 즉시 삭제하지 않아 교사가 잘못 제외했을 때 같은 수업 중 자리를 복구할 수 있게 하고, 세션 종료 시 다른 자료와 함께 삭제한다.

`lastSeenAt`은 상태 표시일 뿐 자동 삭제 근거로 사용하지 않는다. 탭 전환과 학교 Wi-Fi 지연을 고려해 첫 기본값은 다음과 같이 둔다.

- 최근 60초 이내: `접속 중`
- 60초 초과 180초 이내: `응답 지연`
- 180초 초과: `연결 끊김 가능`

수치는 실제 기기 리허설에서 조정한다. 교사의 명시적 확인 없이 참가자를 자동 제외하지 않는다.

### 3-2. 자리 재연결은 토큰 회전으로 처리한다

교사가 참가자 행에서 `자리 다시 연결`을 누르면 서버가 그 참가자에만 유효한 짧은 일회용 복구 코드를 만든다. 학생은 재연결 화면에 코드를 입력하고 새 학생 토큰을 받는다.

- 기존 토큰 해시는 즉시 폐기하고 새 토큰 해시로 교체한다.
- 모둠·역할·단계·제출/공유/확인 상태는 유지한다.
- 복구 코드는 5분 뒤 만료되고 한 번 성공하면 다시 쓸 수 없다.
- 코드 원문은 교사 화면에만 잠시 표시하며 서버 로그·URL·브라우저 장기 저장소에 남기지 않는다.
- 같은 자리에 두 기기가 동시에 붙지 않도록 이전 토큰은 재연결 성공 즉시 무효화한다.

일반 QR 재입장은 새 참가자를 만드는 흐름이고, 자리 재연결은 기존 참가자 토큰을 바꾸는 흐름이다. 두 버튼과 설명을 명확히 분리한다.

### 3-3. 참가자 제외는 단계별 안전 조건을 둔다

교사 화면에서 `참가자 제외`는 확인창과 함께 제공한다. 제외는 학생의 미완료 행동을 완료로 조작하지 않고 관문 분모에서만 뺀다.

- 대기·편성 미리보기: 제외 후 인원과 3/4/5인 편성을 다시 계산한다.
- 역할 확인·최초 판단·자료 말하기: 제외 후 해당 모둠이 시나리오의 최소 3명 조건을 만족할 때만 허용한다. 방 단계와 완료 수를 활성 참가자 기준으로 다시 계산한다.
- 공동 초안 이후: 기본적으로 `자리 다시 연결`을 우선한다. 제외할 경우 현재 초안의 근거 역할과 확인 분모를 재검증한다. 제외된 역할이 초안 근거에 포함돼 유효 근거가 2개 미만이 되면 초안을 무효화하고 모둠을 공동 초안 단계로 돌린다.
- 제외 취소: 동일 자리를 복원하되, 그 사이 초안 revision이 바뀌었다면 복원 학생의 기존 확인은 되살리지 않는다.

역할 공백을 몰래 다른 학생에게 합치지 않는다. 3인 편성은 시나리오에 정의된 공통 자료 규칙을 다시 적용한다.

### 3-4. 진행 mutation을 모둠 단위로 분리한다

새 `sessions.advanceGroupStage(sessionId, groupNumber)`는 해당 모둠의 활성 참가자만 검사한다.

- 역할 확인 → 최초 판단: 별도 완료 조건 없이 해당 모둠의 가장 이른 단계 참가자를 이동한다.
- 최초 판단 → 자료 말하기: 활성 참가자의 `submittedAt`이 모두 있어야 한다.
- 자료 말하기 → 공동 초안: 활성 참가자의 `sharedAt`이 모두 있어야 한다.
- 공동 초안 이후: 기존처럼 같은 revision 전원 확인을 유지한다.
- 조건 미충족 시 누가 어떤 행동을 남겼는지 답 내용 없이 `미완료 1명 · 최초 판단`처럼 구조화된 차단 사유를 반환한다.

교사 모둠 카드의 `이 모둠 다음 단계`는 서버 preflight 결과가 통과한 경우에만 활성화한다. 실패 시 버튼 옆에 차단 사유를 표시한다.

기존 `전체 다음 단계`는 다음 조건에서만 활성화한다.

1. 모든 활성 모둠의 현재 관문이 같다.
2. 모든 활성 모둠이 그 관문을 통과했다.
3. 세션이 진행 중이고 일시정지가 아니다.

조건이 다르면 버튼을 비활성화하고 모둠별 차단 사유 요약을 보여 준다. 전체 버튼이 서로 다른 단계의 모둠을 한 번에 각기 다른 다음 단계로 보내지는 않는다.

### 3-5. 학생 완료 행동은 멱등적으로 만든다

`completeFirst`와 `markShared`는 같은 요청이 반복돼도 이미 완료된 상태라면 성공을 반환한다. 네트워크 응답이 유실된 뒤 학생이 다시 눌러도 빨간 오류로 끝나지 않아야 한다.

학생 UI는 다음 상태를 구분한다.

- 전송 중: 버튼 비활성화와 `저장 중…`
- 성공: `설명 완료`
- 재시도 가능 오류: `연결이 잠시 끊겼어요. 다시 눌러 주세요.`와 `다시 시도`
- 단계가 이미 진행됨: 서버 상태를 다시 불러와 현재 화면으로 이동
- 토큰 무효: `선생님께 자리 다시 연결을 요청하세요.`

서버 오류 원문은 학생에게 그대로 표시하지 않는다. 교사에게도 개인 답 내용은 노출하지 않는다.

### 3-6. 개입 이력과 확인 상태를 모둠 카드에 표시한다

서버에 이미 저장된 `interventions`를 모둠 카드에 연결해 `최근 개입: 힌트 · 10:42`처럼 표시한다. 전송 버튼은 요청 중 비활성화하고 성공 뒤 즉시 최근 이력을 갱신한다.

학생 화면에는 새 개입을 강조하고 `확인했어요`를 제공한다. 참가자별 `interventionId` 확인 행 또는 동등한 세션 한정 상태를 저장해 교사에게 `3/4 확인`으로 보여 준다. 같은 개입을 다시 보내면 새 이력으로 남기되 교사 확인창에서 `같은 종류를 다시 보냅니다`를 알린다.

### 3-7. QR은 토큰을 바꾸지 않고 확대한다

교사 대기 화면에 `QR 크게 보기`를 추가한다. 오버레이에는 현재 QR, 6자리 수업 코드, 활동 제목, 수동 입장 안내, 닫기 버튼을 표시한다.

- 기존 `joinUrl`을 그대로 사용하며 새 입장키를 만들지 않는다.
- 1366×768과 iPad 가로에서 QR 전체와 닫기 버튼이 한 화면에 보인다.
- 터치 닫기, 바깥 영역 닫기, 키보드 `Esc`를 지원한다.
- `QR 새로 만들기`와 색상·문구·위치를 분리한다.

## 5. 검증 계획

### 자동 회귀

1. `npm run check`로 lint, typecheck, 단위 테스트, Convex 통합 테스트, production build를 통과한다.
2. 기존 고조선·고려 초기·조선 후기 시나리오의 3/4/5인 편성을 모두 검사한다.
3. 가상 학생 21명에서 한 학생의 토큰을 잃게 한 뒤 같은 자리에 재연결하고 기존 역할·단계가 유지되는지 확인한다.
4. 재연결 전 토큰과 복구 코드 재사용이 모두 거부되는지 확인한다.
5. 한 참가자를 제외했을 때 해당 모둠의 완료·확인 분모만 줄고 다른 모둠은 변하지 않는지 확인한다.
6. 초안 근거 역할을 제외하면 초안이 무효화되고 확인 수가 0으로 돌아가는지 확인한다.
7. 한 모둠이 막혀도 준비된 다른 모둠의 `advanceGroupStage`가 성공하는지 확인한다.
8. `markShared`를 연속·중복 호출하고 응답 유실을 흉내 내도 성공 상태로 수렴하는지 확인한다.
9. 힌트·심화 전송 이력과 확인 수가 세션 간 섞이지 않는지 확인한다.
10. 세션 종료 뒤 참가자 상태·복구 해시·개입 확인까지 모두 삭제되는지 확인한다.

### 실제 기기 리허설

교사 1명과 학생 역할 기기 4~8대로 다음 순서를 수행한다.

```text
QR 입장
→ 한 기기 탭 종료
→ 교사 화면 연결 끊김 표시
→ 자리 재연결
→ 설명했어요 연속 탭·Wi-Fi 잠시 끊기
→ 한 모둠만 다음 단계
→ 힌트 전송·학생 확인
→ 참가자 한 명 제외·복원
→ 공동 초안 revision 재검증
→ 종료·삭제
```

이 리허설을 통과하기 전에는 21명 재시험을 진행하지 않는다.

## 6. 수용 기준

- 교사가 참가자별 `접속 중/응답 지연/연결 끊김 가능`을 볼 수 있으며 시스템이 자동 삭제하지 않는다.
- 학생이 다른 기기에서 같은 자리로 재연결해 모둠·역할·단계를 복구한다.
- 오래된 학생 토큰과 사용한 복구 코드는 재사용할 수 없다.
- 제외된 참가자는 관문·완료·확인 분모에서 빠지고, 복원 시 현재 revision 기준으로 다시 계산된다.
- 한 모둠의 미완료 참가자가 다른 모둠의 진행을 막지 않는다.
- 전체 다음 단계는 실행 가능한 때만 활성화되고, 불가능할 때 모둠·행동별 이유가 보인다.
- `설명했어요` 중복 탭과 일시적 응답 유실이 학생을 오류 화면에 고정하지 않는다.
- 교사는 모둠별 최근 힌트/심화 종류·시각·확인 수를 볼 수 있다.
- QR 확대 전후 QR 내용과 입장키가 동일하다.
- 추가된 상태와 토큰 해시는 세션 종료 시 모두 삭제된다.
- 학생 식별 정보와 개인 판단 내용은 추가로 수집하지 않는다.

## 7. 범위 밖과 승인 요청

이번 묶음에서는 다음을 하지 않는다.

- 학생 행동을 교사가 임의로 `완료` 처리하는 강제 통과
- 개인 선택·이유·대화 원문의 서버 저장
- 참가자의 장기 출석·기기 추적
- 정규 MUD 28편, `js/mudEngine.js`, 조선 후기 역사 콘텐츠 문안 수정
- 이해도 문제의 일괄 문장 축약 — 별도 3~5명 관찰 뒤 결정

사용자 승인 뒤 `T1~T3`을 첫 구현 묶음으로 진행한다. `T4`와 `T5`는 같은 교사 화면을 수정하지만 P0 회귀가 안정된 다음 별도 목적 단위로 구현한다.
