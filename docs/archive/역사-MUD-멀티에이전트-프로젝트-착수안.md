# 역사 MUD 게임 웹 페이지
## 멀티 에이전트 프로젝트 착수안

> 이 문서는 현재 제작 중인 역사 MUD 게임 웹 페이지를 Codex, Claude Code, Antigravity가 이어서 작업하기 위한 최초 인수인계 문서다.

## 1. 현재 확인된 프로젝트 맥락

- 프로젝트: 역사 MUD 게임 웹 페이지
- 현재 상태: 다른 작업 폴더와 GitHub 저장소에서 주먹구구식으로 제작 중
- 주요 사용자: 현재는 제작자인 나 혼자
- 작업 목적: 여러 코딩 에이전트의 사용량 한도 때문에 작업이 중단되는 문제를 줄이고, 에이전트가 바뀌어도 프로젝트 맥락을 유지한다.
- 이번 1차 목표: 지금까지의 코드와 GitHub 상태를 분석하고, 기획·프론트엔드·디자인·백엔드·데이터베이스·배포 영역을 정리한다.

## 2. 아직 확정하지 않은 사항

다음 항목은 실제 저장소를 확인한 뒤 결정한다.

- 로컬 프로젝트 폴더의 정확한 위치
- GitHub 저장소 주소와 기본 branch
- 현재 기술 스택과 실행 방법
- 프론트엔드·백엔드·데이터베이스의 실제 분리 여부
- 배포 플랫폼과 현재 배포 상태
- 역사 콘텐츠 데이터의 저장 형식
- 기존 폴더를 유지할지, 점진적으로 재구성할지

## 3. 권장 작업 폴더 구조

기존 코드와 파일을 먼저 분석한 뒤, 필요한 문서만 점진적으로 추가한다. 처음부터 모든 폴더를 만들거나 기존 코드를 대량 이동하지 않는다.

```text
history-mud/
├─ 00_project/
│  ├─ PROJECT.md       # 프로젝트 목적과 범위
│  ├─ STATUS.md        # 현재 상태와 다음 작업
│  ├─ WORKFLOW.md      # 에이전트 교대·검토 절차
│  ├─ AGENTS.md        # 모든 코딩 에이전트의 공통 규칙
│  ├─ ROADMAP.md       # 단계별 향후 계획
│  └─ DECISIONS.md     # 중요한 기술·구조 결정
├─ docs/               # 기획, 화면 흐름, 아키텍처, API 메모
├─ src/ 또는 기존 코드 폴더
├─ tests/              # 기존 테스트 또는 새 테스트
├─ public/             # 정적 자산
└─ README.md
```

현재 프로젝트가 이미 다른 구조를 사용한다면, `src/`, `app/`, `frontend/` 등을 즉시 이름 변경하지 않는다. 첫 작업은 구조 파악과 문서화다.

## 4. 에이전트 역할 분담

역할은 모델 이름보다 작업 성격에 따라 배정한다.

| 작업 | 우선 담당 | 보조·검토 |
|---|---|---|
| 저장소 전체 탐색과 현황 정리 | Antigravity | Codex |
| 요구사항·기획·작업 분해 | ChatGPT 또는 Antigravity | 사용자 |
| 핵심 기능 구현 | Codex | Claude Code |
| 프론트엔드·상호작용 구현 | Claude Code 또는 Codex | 다른 에이전트 |
| UI 구조·사용성 개선 | Claude Code | Antigravity |
| 백엔드·API·데이터 연결 | Codex | Claude Code |
| 데이터베이스 구조 검토 | Codex | Antigravity |
| 코드 리뷰·버그 탐색 | 구현하지 않은 에이전트 | 사용자 |
| 배포 설정·실행 점검 | Codex | Claude Code |
| 최종 방향 결정 | 사용자 | 모든 에이전트는 제안만 함 |

초기에는 여러 에이전트가 동시에 같은 파일을 수정하지 않는다.

```text
에이전트 A: 탐색·분석
    ↓
STATUS.md 기록
    ↓
commit
    ↓
에이전트 B: 구현
    ↓
테스트·STATUS.md 기록
    ↓
commit
    ↓
에이전트 C: 검토·수정
```

## 5. 프로젝트 폴더로 이동하는 방법

현재 이 문서는 Edu-Nexus 루트에 있다. 실제 역사 MUD 저장소의 위치를 확인한 뒤, 이 문서를 프로젝트 폴더의 `00_project/` 안으로 복사하거나 이동한다.

권장 최종 위치:

```text
<역사 MUD 로컬 저장소>\00_project\MULTI_AGENT_PROJECT_SETUP.md
```

PowerShell 예시:

```powershell
Set-Location "<역사 MUD 로컬 저장소>"
New-Item -ItemType Directory -Force -Path ".\00_project"
Copy-Item "G:\내 드라이브\Edu-Nexus\역사-MUD-멀티에이전트-프로젝트-착수안.md" ".\00_project\MULTI_AGENT_PROJECT_SETUP.md"
```

실제 경로가 확정되기 전에는 `<역사 MUD 로컬 저장소>`를 임의로 채우지 않는다.

## 6. VS Code 다시 실행 절차

1. 현재 역사 MUD 저장소의 모든 변경사항을 확인한다.
2. 필요한 변경사항을 commit하거나, 작업 중인 변경사항은 별도로 보존한다.
3. VS Code에서 역사 MUD 저장소 폴더를 연다.

```powershell
code "<역사 MUD 로컬 저장소>"
```

4. VS Code의 Codex에서 아래 첫 지시문을 실행한다.

VS Code를 강제로 종료하거나 변경사항을 삭제하지 않는다. 이미 열려 있는 VS Code가 있다면 먼저 현재 파일과 터미널 작업을 확인한다.

## 7. 첫 번째 Codex 지시문

아래 내용을 역사 MUD 프로젝트의 Codex에 그대로 붙여넣는다.

```text
이 저장소는 현재 제작 중인 역사 MUD 게임 웹 페이지 프로젝트다.

이번 작업의 목적은 새 기능을 바로 구현하는 것이 아니라,
현재 프로젝트를 여러 코딩 에이전트가 이어서 작업할 수 있는 상태로 파악하고 문서화하는 것이다.

먼저 다음을 순서대로 수행하라.

1. 현재 작업 디렉터리와 Git 상태를 확인하라.
2. README, package.json 또는 이에 해당하는 실행 설정을 읽어라.
3. 전체 폴더 구조를 확인하되 node_modules, 빌드 결과물, 캐시 폴더는 제외하라.
4. 프론트엔드, 백엔드, API, 데이터베이스, 정적 자산, 배포 설정의 위치를 찾아라.
5. 프로젝트를 실행하는 명령과 테스트 명령을 확인하라.
6. 현재 구현된 기능과 미완성 기능을 실제 코드 기준으로 정리하라.
7. 추측한 내용과 파일에서 확인한 내용을 구분하라.

그 다음 사용자 승인 없이 대규모 리팩터링이나 파일 이동을 하지 말고,
아래 문서 초안을 00_project/에 작성하라.

- PROJECT.md
- STATUS.md
- WORKFLOW.md
- AGENTS.md
- ROADMAP.md
- DECISIONS.md

문서에는 다음 내용을 반영하라.

- 역사 MUD 게임의 현재 목적과 사용자
- 현재 기술 스택과 실행 방법
- 실제 폴더별 역할
- 이미 구현된 기능
- 미완성·미검증 기능
- 프론트엔드·백엔드·데이터베이스·배포의 현재 상태
- 다음 작업 우선순위
- 여러 에이전트가 작업할 때 충돌을 피하는 규칙

문서 작성 후에는 다음을 보고하라.

1. 확인한 프로젝트 구조
2. 변경하거나 새로 만든 파일
3. 실행·테스트 결과
4. 아직 확인하지 못한 사항
5. 다음 에이전트에게 맡기기 좋은 작업 3개

이번 작업에서는 기존 기능을 수정하지 말고, 문서 생성과 분석에 집중하라.
```

## 8. 이후 작업 인수인계 규칙

각 에이전트는 작업 전 다음 파일을 읽는다.

```text
00_project/PROJECT.md
00_project/STATUS.md
00_project/WORKFLOW.md
00_project/AGENTS.md
```

작업 종료 시 다음을 남긴다.

- 완료한 작업
- 변경한 파일
- 실행한 테스트와 결과
- 아직 남은 문제
- 다음 작업
- 다음 에이전트가 알아야 할 주의사항

코드 변경은 가능한 한 하나의 목적 단위로 commit한다. 사용량 한도에 도달하기 직전에는 반드시 `STATUS.md`를 갱신하고, 미완료 작업을 구체적으로 남긴다.

- [x] 현재 기술 스택과 실행 명령을 확인했다.
- [x] 기존 코드 구조를 문서화했다.
- [x] 기존 운영 문서(`PRD.md`, `BACKLOG.md`, `DECISIONS.md`, `project_context.md`, `agents.md`, `walkthrough.md`)를 확인했다.
- [x] Codex가 저장소를 분석하고 결과를 보고했다.
- [ ] PRD·기술 스택·사용자 흐름·플로우차트·와이어프레임을 현재 상태에 맞게 정리한다.
- [ ] 문서에 축적된 작업의 우선순위를 정하고 첫 구현 작업을 한 가지로 좁힌다.
- [ ] 첫 구현 전 사용자에게 범위를 확인받는다.

## 10. 현재 저장소에 적용할 문서 운영 원칙

이 저장소는 이미 구현과 품질 검증이 진행된 정적 웹앱이다. 따라서 최초 착수안의 `00_project/` 문서를 새로 만들기보다, 현재 루트의 운영 문서를 기준으로 작업한다.

### 문서 우선 원칙

수정 요청이나 개선 아이디어가 생겨도 원칙적으로 즉시 코드를 수정하지 않는다.

1. 문제·아이디어·발견 사항을 먼저 `BACKLOG.md`에 기록한다.
2. 교육적 영향, 사용자 영향, 예상 변경 범위, 관련 파일을 함께 적는다.
3. 구현이 필요한 항목은 `idea` 또는 `documented` 상태로 둔다.
4. 정기 검토 시점에 우선순위를 정하고 `planned` 항목을 선정한다.
5. 구현 계획을 승인한 뒤에만 코드를 수정한다.
6. 검증을 통과한 항목만 `completed`로 표시하고 `walkthrough.md`에 기록한다.

### 예외 규칙

학생의 진행을 막는 오류, 배포 장애, 데이터 손상 위험과 같은 P0 문제는 즉시 수정할 수 있다. 단, 수정 후 반드시 원인·변경 파일·검증 결과를 `BACKLOG.md` 또는 `walkthrough.md`에 기록한다.

### 작업 상태

```text
idea → documented → prioritized → planned → in-progress → verified → completed
```

### 정기 우선순위 검토

- 1~2주마다 한 번 우선순위를 검토한다.
- 또는 P0·P1 항목이 3개 이상 쌓이면 조기 검토한다.
- 한 번의 구현 주기에는 하나의 목적 단위만 선정한다.
- 검토 중 발견한 추가 개선점은 현재 작업 범위에 섞지 않고 `BACKLOG.md`에 새로 기록한다.

## 11. 단계별 진행 계획

### Phase 0 — 문서 운영체계 정합화

- [x] 실제 폴더 구조와 실행 환경 확인
- [x] 기존 문서 체계 확인
- [x] 문서 우선·일괄 구현 원칙을 본 착수안에 반영
- [ ] `agents.md`에 동일한 작업 수집·우선순위·구현 규칙 반영
- [ ] `BACKLOG.md` 항목을 현재 상태 기준으로 재분류

### Phase 1 — 제품과 기술 설계 정리

- [ ] 기존 `PRD.md`를 실제 구현 범위와 일치하도록 보완
- [ ] Vanilla JS·Canvas·JSON·localStorage·GitHub Pages 기술 스택 문서화
- [ ] 백엔드·API·데이터베이스가 현재 범위에 없는 이유 기록
- [ ] 학생·교사의 핵심 사용자 흐름 작성
- [ ] Regular MUD, Deep-dive MUD, 퀴즈, 도감 흐름을 플로우차트로 작성
- [ ] 모바일·태블릿 우선 핵심 화면 와이어프레임 작성

### Phase 2 — 설계 검토와 작업 수집

- [ ] 설계 문서에서 발견한 문제를 모두 `BACKLOG.md`에 기록
- [ ] 데이터·화면·시뮬레이터 연결 관계 확인
- [ ] 기능 문제, 교육 품질 문제, UX 문제, 확장 아이디어를 분류
- [ ] 각 항목에 우선순위·예상 영향·관련 파일 추가

### Phase 3 — 구현 묶음 선정

- [ ] P0~P4 기준으로 작업 우선순위 결정
- [ ] 첫 구현 묶음을 하나의 목적 단위로 선정
- [ ] `implementation_plan_*.md` 작성
- [ ] 변경하지 않을 범위와 검증 방법 명시
- [ ] 사용자 확인 후 코딩 시작

### Phase 4 — 구현·검증·기록

- [ ] 계획된 파일만 최소 범위로 수정
- [ ] JSON·MUD·시뮬레이터·JavaScript 검증 실행
- [ ] 모바일·태블릿 회귀 점검
- [ ] `walkthrough.md`에 결과 기록
- [ ] 완료 항목을 `BACKLOG.md`에서 제거하거나 완료 상태로 정리
- [ ] 다음 검토 주기의 작업 순서 갱신

> 현재 다음 작업은 Phase 0의 남은 문서 정합화이며, 그 다음 Phase 1에서 PRD·기술 스택·플로우차트·와이어프레임을 정리한다. 설계 문서가 정리되기 전에는 대규모 코드 변경을 시작하지 않는다.

> 현재 우선순위는 기능을 많이 추가하는 것이 아니라, 프로젝트의 기억을 Git과 문서에 외부화하여 에이전트가 바뀌어도 작업이 끊기지 않게 만드는 것이다.
