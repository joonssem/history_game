별도 앱은 배포 단위이고 별도 저장소는 코드 관리 단위다. B를 추천하지만, 사용자가 하나의 저장소 관리를 선호하면 C도 성립한다. C는 처음부터 Turborepo 등 추가 도구를 요구하지 않는다. Vercel은 모노레포에서 프로젝트별 Root Directory를 지원한다. [Vercel 공식 문서](https://vercel.com/docs/monorepos)

신규 앱 안정화 뒤 기존 허브에 “실시간 수업 입장” 링크를 추가한다. 현재 정적 v0.1은 별도 활동으로 유지한다. 공개 저장소에서는 소스 자체를 숨길 수 없으므로 역할 정보의 비공개는 수업 중 앱 응답의 접근 범위로 정의한다.

## 5. 21명 모둠 구성 추천

**기본은 4·4·4·4·5명(5모둠).** 4인 구성을 가장 많이 유지하면서 한 모둠만 변형한다. 이는 교사의 경험과 이번 활동 구조를 반영한 설계 판단이다. 4명이 언제나 교육학적으로 최적이라는 뜻은 아니다.

EEF 종합 검토는 공동 목표가 있는 3~5인 협동 활동을 유망하게 보며 전원 발화와 과제 구조화를 강조한다. 근거 강도는 낮게 평가하므로 이 게임에서 3인과 5인의 우열을 확정하는 자료로 사용하지 않는다. [EEF 협동학습 검토](https://educationendowmentfoundation.org.uk/education-evidence/teaching-learning-toolkit/collaborative-learning-approaches)

| 21명 구성 | 교육·참여 관점 | 수업 운영 관점 | 프로그램 관점 |
|---|---|---|---|
| 4×4 + 5×1 | 네 관점 구조 유지, 5인은 한 명 소외 방지 필요 | 5모둠만 관찰·발표 관리 | 변형 모둠 하나, 기존 v0.1의 5모둠 범위에도 맞음 |
| 4×3 + 3×3 | 발언 차례를 더 자주 확보할 여지, 3인용 자료 재분배 필요 | 6모둠 순회·발표 관리, 공간 확인 필요 | 가변 모둠 수 필수. 3인 콘텐츠 검증 비중이 커짐 |
| 3×7 | 작은 모둠에서 대화하기 쉬울 수 있음 | 7모둠의 개입·시간 조율 부담 | 4인 중심 설계를 모두 변형해야 함 |

4인에서 가능한 학생 쌍은 6개, 5인은 10개, 3인은 3개다. 이는 대화 조율 관계 수를 설명하는 산술 예시일 뿐 실제 대화량·인지부하의 측정값이 아니다. 짧은 균등 발언 라운드에서 1인 30초라면 각각 2분·2분30초·1분30초가 필요하다. 5인의 추가 30초를 확보하는 편이 6개 모둠으로 전체를 재구성하는 것보다 이번 조건에서는 운영하기 쉽다고 판단한다.

조용한 학생의 참여가 5인 모둠에서 반복적으로 부족하면 다음 활동에 4·4·4·3·3·3을 시험한다. 한 수업에서 다른 모둠의 결과 차이를 인원수 효과로 단정하지 않는다. 학생 조합·읽기·교사 개입도 다르기 때문이다.

## 6. 3·4·5인 역할·정보 설계

학생의 역할은 판단을 강제하는 대본이 아니다. “이 관점에서 무엇을 걱정할까?”를 제시하며 어느 역할이든 증거를 보고 생각을 유지하거나 바꿀 수 있다.

| 인원 | 역할·정보 배치 제안 | 참여 보장 |
|---|---|---|
| 4 | A 피해·생존, B 어려운 사정, C 증거·절차, D 공동 규칙 | 각자 고유 단서, 개인 선택·이유, 자기 정보 설명 |
| 3 | A/B/C 유지. D의 규칙 필요성은 시작 공통 상황으로 짧게 제공. 공유 뒤 “다른 사건에도 적용되는가?” 공통 질문 제공 | 한 학생의 두 역할 겸임 금지. 독립 정보 3개와 공통 자료로 네 관점 유지 |
| 5 | A/B/C 유지. D의 공동 규칙 단서를 D(공동체의 반복 갈등)·E(규칙 적용을 확인하는 사람)의 서로 다른 짧은 단서로 나눔 | E도 단서·최초 판단·발화·법 초안 확인 모두 수행. 단순 서기·진행자 전담 금지 |

예시: 4인 D 카드에 ‘다툼 증가’와 ‘같은 일을 다르게 처리해 갈등’을 담고, 5인에서는 각각 D/E로 나눈다. 3인 공통 상황에도 이 두 핵심 사실을 짧게 넣는다. 학급 전체가 최종 법을 만들기 전에 도달하는 핵심 정보 집합은 동일하게 맞춘다. 3인의 최초 공통 정보량은 달라지므로 모둠 크기별 최초 선택 비율을 실험적으로 동등하다고 취급하지 않는다.

첨부의 “3인에서 증거·절차를 늦게 공개”도 가능하지만, 첫 판단에서 신중하게 사실을 확인하는 관점이 사라질 위험이 있다. 이번에는 C를 유지하고 D를 공통 맥락으로 옮기는 방식을 우선 추천한다. 역할 개수와 핵심 관점 개수를 분리하는 것이 포인트다.

추가 증거는 가족의 굶주림을 반복 공개하는 것으로 끝내지 않는다. 예를 들어 첫 판단 시에는 절도 의심·불완전한 증언을 주고, 이후 ‘가져간 양이 확인됐고 일부 곡식이 돌아왔지만 피해 가구의 겨울 식량은 여전히 모자람’처럼 모든 역할이 새롭게 검토할 사실을 준다. 모두 교육용 허구임을 표시하고 고조선의 실제 사건·재판 절차라고 설명하지 않는다. 사건 2는 반복 절도를 통해 첫 법의 적용 한계를 살피는 다음 버전의 선택 확장이며 첫 MVP에서는 생략한다.

## 7. 다른 인원의 학급과 무작위 편성

- 교사는 당일 참석 수 N을 입력하고 3~5인으로 합계가 N인 크기 배열을 확인한다. 기본 알고리즘은 4인 수를 우선 늘리고, 나머지를 3/5인으로 조정한다. 같은 수준 후보는 교사에게 선택 가능하게 한다.
- 예: 19→4·4·4·4·3, 20→4×5, 21→4×4+5, 22→4×4+3×2 또는 4×3+5×2, 23→4×5+3, 24→4×6, 25→4×5+5. 22명의 기본은 4인 우선 원칙으로 6모둠안을 제시하고 5모둠 대안도 보여 준다.
- 명부 이름을 업로드하지 않고 수업 한정 학생 코드 S01…S21을 배부한다. 무작위 순열을 크기 배열에 차례로 배분하고 교사가 확인·필요시 이동한 뒤 확정한다. 접속 속도나 입장 순서로 모둠을 결정하지 않는다.
- 활동마다 새로 섞되 같은 활동의 사건 1/2에서는 유지한다. 역할도 편성 확정 시 별도로 섞는다. 장기 짝 중복 방지 알고리즘은 학생 추적이 필요하므로 후속 검토한다.
- 참여 인원이 3명 미만이면 자동 시작 대신 교사가 모둠 합치기·정적 버전 진행 등을 선택한다. 시작 전에는 재편성 가능, 시작 후 이탈에는 자동 셔플·기존 답안 삭제를 하지 않는다.
- 소규모·다른 인원은 데이터로 지원하되 최초 검증 규모는 학생 21명+교사 1명이다. 다른 학급 확대 전 동시 세션·권한 격리·기기 규모를 별도로 검증한다.

## 8. 수업·개인정보·관찰 원칙

40분 중 역사 자료 비교 시간을 먼저 확보한다. 입장·자리 이동·읽기 안내 8분, 개인 최초 판단 3분, 정보 공유 6분, 추가 증거·재판단 5분, 법 만들기 6분, 역사 비교 8분, 마무리·여유 4분을 제안한다. 실제 시간은 리허설로 수정하며 다음 버전에서 사건 2를 추가하더라도 역사 비교 시간을 줄이지 않는다.

범금 8조는 현재 전해지는 세 조항을 자료로 비교한다. 학생이 만든 법을 실제 역사와의 일치도나 처벌의 강도로 채점하지 않는다. 당시 사회를 설명하는 자료와 오늘 우리가 옳다고 생각하는 규범을 구분한다. [국사편찬위원회 범금 8조 사료](https://contents.history.go.kr/front/hm/view.do?levelId=hm_001_0060&treeId=010101)

버튼은 읽기·공유의 자기 보고이지 실제 읽기·대화 증거가 아니다. 판단 유지도 근거가 있으면 성공이다. 선택 변경률을 최대화하지 않는다. 교사는 5인 모둠의 다섯째 학생과 미응답·도움 요청 모둠을 우선 관찰한다.

가명 코드는 완전 익명을 보장하지 않는다. 학생 이름·이메일·음성·장기 식별자를 수업 데이터로 수집하지 않고, 교사의 코드 배부 대응표는 앱 밖에서 관리한다. 인증용 임시 식별자와 학습 기록도 보관·삭제 대상으로 본다. 교육용 운영 로그와 향후 연구용 장기 보관은 별개로 결정한다.

## 9. 남은 인터뷰와 다음 결정

현재 인터뷰로 기초 설계는 진행 가능하다. 구현 시작 때 다음을 묶어 확인한다: 사용 교과서·8조법 선행학습 여부, 학교 Wi-Fi에서 실시간 접속 가능한지, 수업 결과를 교사가 며칠 보관할지, 교사 인증에 사용할 로그인 방식·운영 계정, 별도 저장소 관리 선호. 민감한 학생 개인 정보는 요청하지 않는다.

이미 답한 학생 수·시간·무작위 선호·본인 학급 우선은 재질문하지 않는다. 추천안을 채택하면 [MVP 개발 단계](./COLLABORATIVE_MUD_MVP.md)의 첫 수직 슬라이스부터 구현 계획으로 전환한다.

## 10. 후속 검토 — Vercel로 호스팅 통일 가능

TASK-20260906-03. 사용자가 복습 웹앱과 특정 차시 모둠 활동을 같은 제품에서 운영하려는 맥락을 추가로 설명했다. **GitHub Pages 없이 Vercel에서 기존 정적 앱과 신규 실시간 앱의 화면을 모두 운영할 수 있다.** 데이터베이스·실시간 서버 기능은 Convex가 담당한다. Vercel 통일은 Convex까지 Vercel 내부에서 실행한다는 뜻이 아니다. [Vercel 정적 빌드 설정](https://vercel.com/docs/builds/configure-a-build), [Convex의 Vercel 배포 안내](https://docs.convex.dev/production/hosting/vercel)

| 개념 | 관리하는 것 | 서로 독립적으로 정할 수 있는 선택 |
|---|---|---|
| GitHub 저장소 | 코드·콘텐츠·변경 이력 | 하나의 저장소에 여러 앱 관리 가능 |
| Vercel 프로젝트 | 빌드·환경 변수·배포·주소 | 같은 저장소에서 두 프로젝트 배포 가능 |
| 사용자 주소 | 학생이 입장하는 사이트 경로 | 하나의 포털에서 링크 연결, 필요하면 도메인·경로 통합 |
| Convex 배포 | 실시간 공동 상태·권한·데이터 | 협동 활동만 연결, 개인 복습은 DB 없이 유지 가능 |

앞선 별도 저장소 권고는 기존 Pages 운영을 보호하려는 보수적인 선택이었다. 저장소 하나가 기술적으로 위험하거나 정적 앱과 실시간 앱을 함께 둘 수 없다는 의미가 아니다. 사용자가 하나의 교육용 제품으로 관리하려는 맥락에서는 다음 구성이 더 실용적인 초기 후보다.

```text
GitHub: history_game 한 저장소
  기존 정적 파일 → 배포용 정적 산출물 → Vercel 프로젝트 A: 복습·포털
  apps/collaborative-mud/             → Vercel 프로젝트 B: 실시간 협동
                                                   ↕
                                                 Convex
```

학생에게는 포털에서 ‘오늘의 복습’과 ‘모둠 수업 입장’을 제공한다. 내부 프로젝트가 두 개여도 학생이 서비스를 관리할 필요는 없다. Vercel은 같은 저장소에서 프로젝트별 Root Directory를 설정할 수 있다. [Vercel 모노레포](https://vercel.com/docs/monorepos)

**Vercel 프로젝트 하나로도 가능하다.** Next.js 앱이 기존 정적 HTML/CSS/JS/JSON 묶음을 `public/review/`에서 제공하고 새 협동 화면을 별도 route에서 제공할 수 있다. 기존 JS를 모두 React로 다시 작성할 필요는 없다. 다만 기존 정적 진입점은 `/review/index.html` 등 실제 파일 경로로 정하거나 명시적 rewrite를 구성해야 하며 `/review/` 디렉터리의 자동 index 처리를 가정하지 않는다. 파일 단위 public 제공과 경로 충돌을 검증한다. [Next.js public](https://nextjs.org/docs/app/api-reference/file-conventions/public-folder)

단일 프로젝트는 배포·환경 관리가 줄지만 협동 앱의 빌드 실패가 복습 앱 새 버전 배포도 막는다. 두 프로젝트는 빌드·배포 실패 영향을 분리하기 쉽다. 단일 도메인이 필요하면 통합 프로젝트 또는 명시적 라우팅을 별도로 선택하며, 하나의 도메인과 하나의 저장소/프로젝트는 같은 조건이 아니다.

현재 추천은 **저장소 하나·앱 구분·Vercel 프로젝트 둘**이며, 프로젝트까지 하나여야 한다는 운영 요구가 확인되면 정적 자산을 함께 제공하는 통합안을 선택한다. 프레임워크 없는 JavaScript도 Convex 클라이언트를 사용할 수 있으므로 DB 사용 자체가 Next.js 전환을 강제하지 않는다. Next.js는 새 협동·교사 화면을 관리하기 위한 후보다. [Convex JavaScript 클라이언트](https://docs.convex.dev/client/javascript/overview)

이전 시 실제 확인할 사항:

- 기존 fetch·CSS·JS 경로는 상대경로다. HTML만 옮기거나 포괄 rewrite만 추가하지 않고 디렉터리 구조·하위 직접 진입·새로고침·후행 슬래시를 검증한다.
- 정적 배포 산출물은 필요한 HTML/CSS/JS/JSON/이미지만 복사해 구성한다. 루트를 통째로 공개해 새 Next/Convex 코드·환경 파일·문서가 섞이지 않도록 한다. `.gitignore`와 배포 출력 범위를 앱 추가 때 명시한다.
- 주소가 바뀌면 기존 도감·협동 localStorage 기록은 자동으로 이전되지 않는다. 기록 유지 필요 시 이전 주소에서 내보내기→새 주소 불러오기를 설계한다. [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)
- 현재 workflow는 품질 검사다. 정적 검사와 신규 앱 typecheck/build를 배포 과정과 연결한다. Convex preview와 실수업 DB도 분리한다.
- Vercel에서 기존 기능을 확인한 뒤 기본 수업 링크를 바꾸는 순서를 권한다. GitHub Pages를 영구 병행할 필요는 없으며 종료 여부는 이전 검증 후 결정한다.

## 11. 개발·디자인·교육 관점의 현재 평가

평가 범위는 로컬 주요 코드·대표 콘텐츠 및 배포 포털·개인형 고조선 첫 화면의 실제 브라우저 관찰이다. 모든 시나리오·기기·학습 효과를 전수 평가하지 않았다. 아래는 구현 지시나 검증된 수업 효과가 아닌 개선 의견이다.

### 개발 관점

현재 JSON 콘텐츠 분리, 기존 엔진의 재사용, 자동 계약·런타임 검사, 별도 협동 폴더는 점진적 확장에 도움이 된다. 기존 복습 앱의 프레임워크 전면 변경은 우선순위가 낮다. 다음에는 콘텐츠의 ‘공개 지식’과 학생의 ‘현재 공동 상태’를 분리하고, 협동 세션의 소유권·재접속·합의를 먼저 구현하는 것이 가치가 크다.

현재 핵심 복습 기능은 DB 없이 제공할 수 있다. Convex는 학생별 정보·모둠 공동 법·교사 공개 시점처럼 여러 화면이 공유해야 하는 상태에 집중한다. 기존 개인 저장까지 모두 서버화하면 이득이 확인되지 않은 운영 부담이 늘 수 있다.

### 디자인 관점

실제 포털은 한지색 배경·먹색 본문·절제된 강조색과 차시/교과서 쪽수 카드가 일관돼 있다. 캔버스 대체 버튼도 확인했다. 현재 화면에는 퀴즈·도감·협동·단원·Deep-dive·미니게임 등 진입점이 많고, 긴 단원 탭은 관찰한 화면에서 가로 스크롤을 요구했다.

학생 첫 화면에서는 교사가 지정한 오늘 활동의 이름·시간·혼자/모둠 여부가 먼저 보이면 좋겠다. 전체 자료 탐색은 계속 제공하되 첫 행동과 경쟁하지 않도록 배치한다. ‘Regular/Deep-dive/MUD/허브/파일럿’은 문서에서는 유용하지만 학생용 버튼에서는 ‘혼자 복습하기/함께 해결하기/더 탐구하기’처럼 행동을 말하는 표현을 추천한다.

협동 화면은 읽기→개인 판단→화면에서 눈을 떼고 대화→결과 확인의 리듬을 지원한다. 한 화면에 계속 많은 버튼을 배치하기보다 현재 해야 할 행동을 분명하게 한다. 이는 미술 스타일 교체보다 정보 우선순위 개선에 가깝다.

### 교육 설계 관점

복습과 협동 활동은 서로 다른 역할로 발전시키는 편이 좋다. 짧은 복습은 배운 사실·관계를 회수하고, 협동 활동은 근거를 교환하며 판단을 검토하고, 확장 탐구는 관심 주제를 더 깊게 살피도록 한다. 복습 활동을 일률적으로 40분으로 늘릴 필요는 없다.

대표 개선점은 선택지의 사고 요구다. 실제 고조선 첫 단계에는 ‘백성을 이롭게 한다’와 ‘백성을 괴롭히고 곡식을 빼앗는다’가 대비돼 있다. 이 구성은 역사 자료를 이해하지 않아도 좋은 말로 답을 찾을 여지가 있다. 예를 들어 자료에서 당시 사회의 재산·질서와 연결되는 근거를 고르고 설명하게 하면 역사적 이해를 더 직접 확인할 수 있다. 구체 문안은 사실 회수 문항과 가치 판단 문항을 구분해 검토한다.

자료 세 곳을 터치하게 하는 장치는 진행 속도를 조절하지만 이해를 보장하지 않는다. 클릭 수·완료 시간에 더해 ‘어떤 단서 때문에 그렇게 생각했는가’를 작은 응답으로 확인한다. 4분 완료 자체는 실패 판정이 아니며, 그 시간 안에 학습 목표를 달성했는지가 기준이다.

PC통신 MUD에서 가져올 핵심은 텍스트로 상상하고, 다른 사람이 가진 정보가 필요하며, 공동 선택으로 모두가 보는 상황이 달라지는 경험이다. 실시간 DB는 모둠 법이 모든 기기에 나타나고 다음 사건에서 그 법의 결과를 함께 살피도록 지원한다. 첫 버전은 법 공동 확인까지, 이후 검증된 경우에만 선택 결과의 후속 사건 분기를 추가한다. 사료로 확인하는 사실·가상 선택 결과·현대적 가치 판단은 구별해서 보여 준다.

우선순위 제안은 오늘 활동 진입 명확화, 대표 복습 문항의 근거 연결, 고조선 한 모둠 실시간 시제품, 실제 수업 관찰 순서다. 효과가 확인된 패턴부터 확장하며 시나리오 수·게임 시스템 수를 성공 지표로 삼지 않는다.

## 12. 원소스 멀티유즈 파이프라인과 타이머 페이싱 (2026-09-06 결정)

### 12-1. 두 벌이 아니라 한 콘텐츠, 두 활용

사용자 결정: **정적 버전과 실시간 버전은 별개 제품이 아니다.** 하나의 콘텐츠를 만들어 두 방식으로 활용한다.

```text
아이디어 확장·고도화
   → 정적 협동 MUD 제작 (GitHub Pages, DB 없음)   ← 실제 수업으로 검증
      → 같은 콘텐츠를 Vercel + Convex로 발전       ← 교사 대시보드·모둠 단위 진행
```

정적 버전이 갖는 세 가지 역할:

1. **콘텐츠 검증 단계.** 학습 흐름이 성립하는지를 서버 없이 먼저 확인한다.
2. **다른 교사 배포본.** 실시간 버전은 사용자 본인 학급 전용이며 다른 교사용 기능(초대·다중 테넌시·문의 대응)을 만들지 않는다. 다른 교사에게는 정적 버전 주소를 제공한다. 학생 데이터가 기기 밖으로 나가지 않으므로 개인정보 부담도 없다.
3. **실시간 장애 시 폴백.** 실시간 서비스가 멈추면 같은 기기에서 정적 버전으로 계속 진행한다. 종이 카드는 사용하지 않는다.

따라서 시나리오 텍스트(역할별 단서·선택지·추가 증거·역사 자료·페이싱 값)는 **한 곳에서 관리**한다. 렌더링 로직은 두 벌이어도 되지만 콘텐츠는 한 벌이다.

### 12-2. 종이 단계 폐기

**기기 화면이 곧 역할 카드다.** 정적 협동 MUD는 1인 1기기에서 학생마다 다른 정보를 보여 주므로, 종이 역할 카드가 하던 일을 이미 대신한다. 따라서:

- 선사시대 파일럿의 "종이 리허설 먼저" 단계를 폐기한다. 같은 노력으로 정적 웹을 만드는 편이 검증도 정확하고 재사용도 된다.
- 네트워크 장애 대비의 종이 폴백도 폐기한다. 정적 버전이 더 빠르고 준비물이 없다.
- 기존 종이 카드 문안(선사 3막 등)은 버리지 않고 **정적 협동 MUD의 콘텐츠 원본**으로 재사용한다.

남는 조건: 정적 버전은 GitHub Pages에서 받아야 하므로 **학교 인터넷 전체가 끊기면 폴백도 안 된다.** 실시간 서비스 장애와 인터넷 장애를 구분해서 본다.

### 12-3. 타이머 기반 힌트·추가활동

활동 시작 시 고르는 **5분형/10분형이 곧 시간 예산**이 된다. 진행 상황 바를 그 예산과 비교해 느리면 힌트를, 빠르면 추가 활동을 제시한다.

```text
선택한 활동 길이 → 단계별 목표 시간
실제 경과 시간 vs 현재 단계 → 판정
   느림  → 힌트 (질문 형태)
   빠름  → 추가 활동 (깊이, 진도 아님)
   정상  → 개입 없음
```

**이 방식은 서버가 없어도 작동한다.** 각 기기가 자기 시계와 자기 진행도만 알면 되므로 **정적 버전에서 먼저 구현**하고, 실시간 버전에서는 교사가 덮어쓸 수 있게 얹는다. 원소스 멀티유즈의 대표 사례다.

설계 규칙:

- **페이싱 값은 콘텐츠가 소유한다.** 시나리오 데이터에 활동 길이별 단계 목표 시간을 넣어 두 버전이 같은 값을 쓴다.
- **판정은 관대하게.** 목표 대비 편차가 상당히 벌어졌을 때만 반응한다. 예민하면 계속 개입이 떠서 오히려 방해가 된다.
- **힌트는 답이 아니라 질문이다.** `"곡식을 가져간 사람의 사정을 들어 보았나요?"`는 되고 `"두 번째 조항을 보세요"`는 안 된다. 답을 주면 학생이 스스로 알아내는 대신 기다리게 된다.
- **대화를 끊지 않는다.** 힌트를 팝업으로 화면을 덮지 말고 작은 배지·버튼으로 띄운다. 모둠이 토의 중일 때 화면이 가로막히면 2026-09-04 수업에서 확인된 가장 큰 성과(대면 대화)를 깎아먹는다.
- **빠른 모둠에게는 진도가 아니라 깊이를 준다.** `"우리 법은 누구에게 불리할까?"` 같은 심화 질문이며, 다음 단계로 먼저 보내지 않는다. 진도를 빼면 모둠 간 격차가 벌어져 전체 발표가 맞지 않는다.
- **카운트다운 숫자를 학생에게 보이지 않는다.** 남은 시간이 초 단위로 보이면 초등학생은 대화를 줄이고 버튼을 누른다. 진행 바 정도로 제한한다.

정적·실시간의 정확도 차이:

| | 무엇을 잴 수 있나 | 한계 |
|---|---|---|
| 정적 | 개인 기기의 진행도 | 모둠 대화가 병목이어도 개인이 빨리 누르면 빠른 것으로 보인다 |
| 실시간 | **모둠 전체의 진행도** | 실제 병목을 정확히 잡는다 |

이 차이가 실시간 버전이 주는 실질 가치 중 하나다. 정적에서는 근사치로 운영하고, 실시간에서 정확해진다.
